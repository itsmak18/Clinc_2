### F-P6-1 — Missing alert for Server-Sent Events (SSE) connection saturation

**Severity: LOW (Defense-in-depth) · Confidence: HIGH · Blast: System Availability · Status: ✅ FIXED 2026-06-07**

> **Resolution:** Added the `SSEConnectionsHigh` alert rule to `prometheus-alerts.yml` under the `medicore-api-alerts` group. The alert triggers if `sse_active_connections` exceeds 400 (80% of the `SSE_MAX_CONNECTIONS` limit of 500) for more than 5 minutes, giving operators time to scale the api process or investigate connection leaks before new connections fail or get evicted.

**Severity: MEDIUM (Operational resilience) · Confidence: HIGH · Blast: Backups · Status: ✅ FIXED 2026-06-07**

> **Resolution:** Replaced the CommonJS dynamic `require("fs")` call in `scripts/backup-verify.mjs` with proper ES module imports of `openSync`, `readSync`, and `closeSync` at the top of the file, preventing runtime ESM crash during the nightly backup execution.

### F-P6-3 — Unix-only shell pipeline in `backup-verify.mjs` restore drill

**Severity: MEDIUM (Operational resilience / developer usability) · Confidence: HIGH · Blast: Restore drills · Status: ✅ FIXED 2026-06-07**

> **Resolution:** Refactored `runRestoreTest` to perform GPG decryption (if active) and gzip decompression natively in Node using `zlib.gunzipSync`, and then feed the resulting SQL buffer directly into the standard input of `spawnSync("psql", ... )`. This removes Unix-specific shell pipeline commands (`sh`, `zcat`), ensuring the quarterly restore drill can run successfully on Windows developer machines.

---

### F-P6-4 — Unrecognized SQL parameters crash during restore drills

**Severity: LOW (Operational resilience) · Confidence: HIGH · Blast: Restore drills · Status: ✅ FIXED 2026-06-07**

> **Resolution:** Added a compatibility filter inside `scripts/backup-verify.mjs` `runRestoreTest` that converts the decompressed SQL buffer to a string and strips `SET transaction_timeout = ...` parameters before feeding it to `psql`. This ensures that SQL dumps generated by newer `pg_dump` tools on developer machines (such as PG 18.4) can be restored into PostgreSQL 16 containers without triggering parameter mismatch errors and aborting the restore.

### F-P6-5 — Alertmanager never delivers any alert email (`${VAR}` not interpolated)

**Severity: CRITICAL (observability defeat) · Confidence: HIGH · Blast: every alert · Status: ✅ FIXED 2026-06-07 (Mike: hardcode + `_file` secret)**

> **Resolution:** `monitoring/alertmanager/alertmanager.yml` now hardcodes the
> non-secret SMTP fields and reads the password via
> `smtp_auth_password_file: /run/secrets/smtp_auth_password`; the receiver `to:`
> addresses are hardcoded. `docker-compose.prod.yml` drops the inert `environment:`
> block on the alertmanager service and registers the `smtp_auth_password` Docker
> secret. The false "Alertmanager supports `${VAR}` interpolation" claim in
> `CLAUDE.md` is corrected. **Pre-launch verify (added to checklist):** trigger a
> synthetic alert via `amtool alert add` and confirm the email is delivered — rule
> reload alone does NOT prove delivery. **Runtime-verify before cutover** (no live
> SMTP in this session).


`monitoring/alertmanager/alertmanager.yml:16-19,38` sets `smtp_smarthost: "${SMTP_SMARTHOST}"`,
`smtp_from`, `smtp_auth_username`, `smtp_auth_password`, and the receiver `to: "${ALERT_EMAIL_TO}"`.
`docker-compose.prod.yml:629-634` passes those as `environment:` vars and comments
*"Allow env-var interpolation in alertmanager.yml"*; `CLAUDE.md` ("Never Do This")
enshrines the same belief: *"Alertmanager's YAML supports `${VAR}` interpolation."*

**That belief is false.** Alertmanager does **not** expand environment variables in
its config file — it is a long-standing, explicitly-declined feature
([prometheus/alertmanager#2818](https://github.com/prometheus/alertmanager/issues/2818)).
The compose runs the stock image with only `--config.file/--storage.path/--cluster.listen-address=`
(`docker-compose.prod.yml:624-628`) — **no `envsubst` entrypoint**. So `smtp_smarthost`
is the literal string `${SMTP_SMARTHOST}`; at send time Alertmanager tries to dial a
host named `${SMTP_SMARTHOST}`, fails, and the notification is dropped (logged, never
delivered). **Every alert in `prometheus-alerts.yml` fires in the Alertmanager UI but
reaches no human** — including the HIPAA breach-detection alerts `AuditLogPermanentLoss`,
`AuditIntegrityMismatch`, and `BackupStale`. This is the exact F-01/F-P4-1 pattern: a
control documented as active that is inert in production.

**Why the first pass missed it:** the go-live checklist's "Prometheus Alerting
verification" step only `POST`s `/-/reload` to Prometheus (validates *rule syntax*),
never sends a test notification through Alertmanager → SMTP.

**Fix (decision required — see question to Mike):** eliminate config-file env interpolation.
Recommended: hardcode the non-secret SMTP fields (smarthost/from/to/user) directly in
`alertmanager.yml` and read the password via `smtp_auth_password_file: /run/secrets/smtp_auth_password`
(Alertmanager natively supports `_file` variants), add that Docker secret, and drop the
`environment:` block. Alternatives: an `envsubst` entrypoint wrapper, or a deploy-time
config render. **Non-regressable guard:** add a go-live step that triggers a synthetic
alert (`amtool alert add`) and confirms the email lands, plus a CI `amtool check-config`.
Correct the false claim in `CLAUDE.md`.

### F-P6-6 — No process-down / target-down alert

**Severity: HIGH (availability blind spot) · Confidence: HIGH · Blast: full outage undetected · Status: ✅ FIXED 2026-06-07**

`prometheus-alerts.yml` had no `up == 0` rule. `HighErrorRate` is a ratio over
`rate(http_requests_total[5m])` — when the api or worker process is fully down it serves
zero requests, the series goes stale, and the ratio is undefined → **a complete outage
pages no one.** Prometheus scrapes both `medicore-api` and `medicore-worker`
(`monitoring/prometheus/prometheus.yml:16-32`) so the synthetic `up` sample exists; it
just wasn't alerted on.

> **Resolution:** Added `ServiceDown` (`up{job=~"medicore-api|medicore-worker"} == 0`,
> `for: 1m`, severity critical) to the `medicore-api-alerts` group. Needs no exporter.

### F-P6-7 — SSL/edge probe alerts inert (`${BLACKBOX_TARGET}` not interpolated)

**Severity: MEDIUM (cert-expiry & edge-availability blind spot; ↓ vs public-internet because D1 = LAN/VPN) · Confidence: HIGH · Status: ✅ FIXED 2026-06-07**

> **Resolution:** `monitoring/prometheus/prometheus.yml` blackbox-tls target is now
> a hardcoded, operator-edited edge URL (`https://clinic.yourdomain.local`) instead
> of the never-expanded `${BLACKBOX_TARGET}`. With a real target, `probe_success`
> and `probe_ssl_earliest_cert_expiry` series exist, so the new `EdgeProbeDown` rule
> and `SSLCertificateExpiringSoon` become live. Requires a Prometheus `/-/reload`
> after the operator sets the URL. **Runtime-verify before cutover.**


`monitoring/prometheus/prometheus.yml:58-64` targets `"${BLACKBOX_TARGET}"`. Prometheus
does **not** env-expand its config file
([prometheus/prometheus#2357](https://github.com/prometheus/prometheus/issues/2357),
[discussion #13381](https://github.com/prometheus/prometheus/discussions/13381)) and the
compose has no render step. The blackbox-tls job therefore probes a literal target
`${BLACKBOX_TARGET}` → `probe_ssl_earliest_cert_expiry` and `probe_success` never exist
for the real domain → `SSLCertificateExpiringSoon` can never fire (cert can silently
expire → clinic outage), and RUNBOOK §7's "stop Caddy → alert fires in 5 min" chaos
criterion is unmeetable. **Cross-check:** I added an `EdgeProbeDown` rule and corrected
the stale "exporters NOT yet deployed" comment, but the rule stays dormant until the
target resolves. **Fix:** hardcode the domain in `prometheus.yml` (it is not a secret),
or use `file_sd`/a rendered config. D1 (LAN/VPN, possibly internal TLS) lowers severity
but does not close it.

### F-P6-8 — Restore drill proves bytes replay, not app usability (no `medicore_app` grants/role post-restore)

**Severity: MEDIUM-HIGH (DR correctness; surfaces only during a real restore) · Confidence: HIGH · Status: ✅ FIXED 2026-06-07**

> **Resolution:** (1) `backup-verify.mjs --restore` gained `checkAppRoleUsability()`
> (Step 4d): it recreates `medicore_app` + re-applies the migration 0020 grants and
> the 0026 audit_logs REVOKE on the restored DB (both stripped by `--no-acl`), then
> connects **as `medicore_app`** and asserts `medicore_app,f,f` (non-superuser,
> non-bypassrls → RLS binds) and that it can `SELECT count(*) FROM patients`. The
> drill now **fails** if the app role can't be made usable, instead of passing as
> superuser. (2) RUNBOOK §2.2 adds step 6 (recreate role + grants, with the exact
> SQL) for a real DR restore; §12.2 documents the new automated drill check.
> `node --check` clean. **✅ Runtime-verified on real PG16 (2026-06-07):** ran the full
> `--restore` drill (fresh migrated source → scratch target) end-to-end, exit 0 —
> `medicore_app usability verified: non-superuser, RLS-binding, reads tenant tables`.
> **Verification caught a bug in the check itself:** the role probe used SQL `||`
> concatenation, which renders booleans as `false` (so it produced
> `medicore_app,false,false` and the assertion `== "medicore_app,f,f"` failed even
> though the role was correct). Fixed to `format('%s,%s,%s', current_user, rolsuper,
> rolbypassrls)` (boolean output → `f`); re-ran → drill green. Classic case for
> running the control, not just reading it.


`backup-verify.mjs` dumps with `--no-owner --no-acl` (`runDump`), and both the quarterly
drill (RUNBOOK §12, restores as the `postgres` superuser into a fresh `medicore_restore`
DB) and the documented production restore (RUNBOOK §2.2) **only validate as superuser**
(row counts, audit-integrity status). But `--no-acl` strips every `GRANT` to
`medicore_app`, and a `medicore_app` role does not exist in a freshly provisioned cluster
(roles are cluster-global, not in a single-DB plain dump). So after a **real** DR restore,
api/worker — which connect as `medicore_app` (NOSUPERUSER) — get *permission denied* on
every table (or *role does not exist*), at the worst possible moment. The drill gives
false green because it never connects as the app role. **Fix:** RUNBOOK §2.2 must add a
post-restore step that recreates `medicore_app` + re-applies the migration 0020 grants
(and the 0026 audit_logs REVOKE), and the drill (§12 / `backup-verify.mjs --restore`)
should connect as `medicore_app` and assert it can read a tenant table inside
`runInTenantContext` (proves RLS + grants), not just `SELECT COUNT(*)` as superuser.

### F-P6-9 — `scripts/load-test.js` is a smoke test, not a load test

**Severity: LOW (Phase 8.5 overlap) · Confidence: HIGH · Status: ✅ FIXED 2026-06-07 (script written; runtime-verify pending)**

`scripts/load-test.js` only GETs `/api/healthz/ready` and `/metrics` — no auth, no
clinical write path (booking, patient list, dashboard), so its `p(95)<500ms` threshold
measured a static health check, not the system under realistic load. Default
`http://localhost:3000` also pointed at Grafana's port, not the API.

> **Resolution:** Rewrote `scripts/load-test.js` as a real k6 load test: `setup()`
> logs in (seed creds), captures the `clinic_token`+`_csrf` cookies, and discovers a
> patient/doctor id; each VU then exercises the **dashboard** (`/dashboard/summary`,
> `/dashboard/recent-activity`), clinical **reads** (`/patients`, `/appointments`,
> `/appointments/today`, `/schedule/doctors`), and the **booking** write
> (`POST /appointments` with `X-CSRF-Token`) under a 0→20→0 VU ramp. Separate
> thresholds: reads `p(95)<500ms`, booking `p(95)<1500ms`, `http_req_failed<1%`,
> `booking_hard_errors<1%` (5xx/401/403). Booking treats 201/409/422 as acceptable
> business outcomes so the run measures latency/stability, not seed-data success.
> `node --check` clean. **Runtime-verify:** `k6 run scripts/load-test.js` against a
> running stack (k6 not installed in this session).

## Staging & Go-Live Checklist (gated by D1/D2)

Below is the consolidated pre-flight checklist for deploying the first pilot instance of Clinic-Hub:

### 1. Secrets & Directory Setup
- Create a directory `./secrets` on the production host (mode `0700`, owned by the deploy user).
- Generate the following cryptographically secure passwords and credentials into individual files inside `./secrets/` (mode `0600`):
  - `postgres_password`: `openssl rand -base64 48 > ./secrets/postgres_password`
  - `app_db_password`: `openssl rand -base64 48 > ./secrets/app_db_password`
  - `redis_password`: `openssl rand -base64 48 > ./secrets/redis_password`
  - `session_secret`: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))" > ./secrets/session_secret`
  - `field_encryption_key`: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))" > ./secrets/field_encryption_key`
  - `metrics_token`: `openssl rand -hex 32 > ./secrets/metrics_token`
  - `grafana_password`: `openssl rand -base64 32 > ./secrets/grafana_password`
  - `smtp_auth_password` (F-P6-5): `printf '%s' '<smtp-app-token>' > ./secrets/smtp_auth_password` — Alertmanager reads this via `smtp_auth_password_file`. Use an app-specific token.
  - `backup_ssh_key`: `ssh-keygen -t ed25519 -N "" -f ./secrets/backup_ssh_key`
  - `jwt_private_key` & `jwt_public_key` (generate atomically):
    ```bash
    node -e "const c=require('crypto');const kp=c.generateKeyPairSync('ed25519',{privateKeyEncoding:{type:'pkcs8',format:'pem'},publicKeyEncoding:{type:'spki',format:'pem'}});require('fs').writeFileSync('./secrets/jwt_private_key',kp.privateKey);require('fs').writeFileSync('./secrets/jwt_public_key',kp.publicKey)"
    ```

### 2. Environment Configurations (`.env`)
Ensure the following variables are declared in `.env`:
```env
API_IMAGE=registry/medicore-api:<tag>
WORKER_IMAGE=registry/medicore-api:<tag>
CADDY_IMAGE=caddy:2.8-alpine
PGBOUNCER_IMAGE=pgbouncer/pgbouncer:1.23
REDIS_IMAGE=redis:7-alpine
ALLOWED_ORIGINS=https://clinic.yourdomain.local
CADDY_DOMAIN=clinic.yourdomain.local
BACKUP_GPG_RECIPIENT=backup@yourdomain.local
BACKUP_RSYNC_TARGET=backup-user@backup-host:/path/to/backups
```

> **SMTP is no longer configured via `.env`** (F-P6-5). The non-secret SMTP fields
> (smarthost / from / to / username) are edited directly in
> `monitoring/alertmanager/alertmanager.yml`; the password is the
> `./secrets/smtp_auth_password` file above. Set the blackbox edge URL (F-P6-7)
> directly in `monitoring/prometheus/prometheus.yml` — neither config file
> env-expands `${VAR}`.

### 3. GPG Key Setup
- Generate or import the GPG public key for `BACKUP_GPG_RECIPIENT` into the backup container's mounted keyring directory `${GNUPG_HOME:-/root/.gnupg}` so that daily backups can be encrypted successfully.

### 4. Verification steps after docker compose up
1. **Verification of Non-Superuser App role RLS:**
   ```bash
   docker compose exec api sh -c 'node -e "const{Pool}=require(\"pg\");const p=new Pool({connectionString:process.env.DATABASE_URL});p.query(\"SELECT current_user,rolsuper,rolbypassrls FROM pg_roles WHERE rolname=current_user\").then(r=>console.log(r.rows[0])).then(()=>p.end())"'
   ```
   *Expected output:* `{ current_user: 'medicore_app', rolsuper: false, rolbypassrls: false }`
2. **Prometheus Alerting verification:**
   Reload alert rules (rule-syntax only) after editing the blackbox edge URL:
   ```bash
   docker compose -f docker-compose.prod.yml exec prometheus wget -qO- --post-data='' http://localhost:9090/-/reload
   ```
   Then confirm targets are UP (no `${...}` literals) and the blackbox series exists:
   ```bash
   docker compose -f docker-compose.prod.yml exec prometheus \
     wget -qO- 'http://localhost:9090/api/v1/query?query=up' | grep -o '"job":"[^"]*"'
   # expect: medicore-api, medicore-worker, redis, node, blackbox-tls — all value "1"
   ```
2b. **Alert DELIVERY verification (F-P6-5 — rule reload does NOT prove this):**
   Trigger a synthetic alert and confirm the email actually lands in the on-call inbox:
   ```bash
   docker compose -f docker-compose.prod.yml exec alertmanager \
     amtool alert add ServiceDown severity=critical \
     --alertmanager.url=http://localhost:9093
   # then check the ALERT_EMAIL_TO inbox; if nothing arrives, check
   # `docker compose logs alertmanager` for SMTP dial errors.
   ```
3. **Manual Backup seed:**
   Run a manual backup to seed the `known_hosts` signature and verify offsite upload connectivity:
   ```bash
   docker compose -f docker-compose.prod.yml exec backup node scripts/backup-verify.mjs
   ```
