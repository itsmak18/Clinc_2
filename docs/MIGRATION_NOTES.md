# Migration Notes — Lessons Learned / Deprecated Approaches

- **Typed config module — `process.env` reads must go through `lib/config.ts` (2026-06-29)**: `artifacts/api-server/src/lib/config.ts` is the single source of truth for all env vars. It reads and defaults them at module init time, exporting a frozen typed object. An ESLint `no-restricted-properties` rule (`"error"` severity) blocks direct `process.env` reads everywhere except `lib/config.ts`, `src/tests/**`, and `src/scripts/**`. **Exception — dynamic flags:** `auth-constants.ts` Phase 2 helpers (`isPhase2Enabled()`, etc.) intentionally still read `process.env.PHASE2_*` directly at call time (not `config.phase2*`) because vitest fork isolation runs each test file in a separate worker; `beforeAll` env mutations happen *after* module collection, so a static `config` constant evaluated at import time would be frozen at the wrong (off) value for the flagON test file. All other env reads are static + in config. **Rule:** do NOT add `config.phase2*` alternatives to `auth-constants.ts` — the dynamic re-read is intentional. When all Phase 2 flags are permanently on (kill-switch removed), consolidate.

- **`i18n.tsx` locale files — split EN/AR dictionaries out of the provider (2026-06-29)**: `hooks/i18n.tsx` now imports from `hooks/locales/en.ts` and `hooks/locales/ar.ts` and re-exports `export const translations = { en, ar }`. The `translations` named export shape is unchanged (`DischargeSheet.tsx` imports and indexes `translations[printLang][key]`; the `t()` function signature `key: keyof typeof translations.en` still holds). **Rule:** add new keys to BOTH locale files (the `i18n.test.ts` EN/AR parity guard fails CI on any mismatch). The locale files are `as const` — TypeScript infers the key union automatically; no manual type declaration needed.

- **`void logAudit` / `void logRead` is a bug, not a perf optimization (2026-06-29)**: All fire-and-forget `void logAudit(...)` and `void logRead(...)` calls across 15+ services were upgraded to `await`. The `void` pattern silently swallowed errors (including outbox-insert failures that should increment `audit_outbox_write_failed`) and caused out-of-order rows under load. **Rule:** always `await` `logAudit` and `logRead`. If you want non-blocking, wrap in a void IIFE and set a timeout — never just `void` at the call site.

- **Break-glass events must use `auditBreakGlass()`, not `logAudit()` (2026-06-29)**: `logAudit()` writes to `audit_outbox` (best-effort, 5-retry max, then counted in `audit_log_write_failures_total`). For emergency-access events (`BREAK_GLASS_*`) a single permanent outbox failure drops the HIPAA §164.312(a)(2)(ii) control record. `auditBreakGlass()` (from `lib/break-glass-audit.ts`) writes directly to `audit_logs` (synchronous, durable), with a JSONL fallback to `BREAK_GLASS_AUDIT_FALLBACK_DIR` if the DB is degraded. The 60-second background reconciler + graceful-shutdown drain flush the fallback into `audit_logs`. **Rule:** any new break-glass event (`BREAK_GLASS_ACTIVATED`, `_DENIED`, `_REVOKED`, `_ACCESS`) must call `auditBreakGlass()`, not `logAudit()`. Never silence the result — `await` it.

- **Migration 0038 — imaging status RENAME VALUE (drizzle emits DESTRUCTIVE; hand-correct it) + `imaging_attachments` table (2026-06-21)**: Renamed `xray_status`/`ultrasound_status` enum values `pending/uploaded/reviewed → requested/in_progress/completed`. **drizzle-kit cannot express an enum-value rename** — it generated `ALTER COLUMN status TYPE text → DROP TYPE → CREATE TYPE(new values) → ALTER COLUMN … USING status::new_type`, whose final cast **fails on any DB holding existing `pending`/`uploaded`/`reviewed` rows** (those labels are absent from the new enum), i.e. it would abort on every populated environment. The generated SQL body was **replaced by hand** with six `ALTER TYPE … RENAME VALUE 'old' TO 'new'` statements (rows + column defaults migrate transparently, transaction-safe). The drizzle-produced meta snapshot already records the final enum values, so it was left untouched and `migration-drift` stays clean. **Rule:** any enum-value *rename* must be hand-authored as `RENAME VALUE` — never accept drizzle's drop/recreate (it's a data-destroying cast). This is distinct from an enum *add* (0032, fine) and *remove* (needs the type-swap recreate). The same migration adds the new clinic-bearing `imaging_attachments` table — it carries the full tenant-isolation standard (CHECK `clinic_id > 0` + dormant 0015 `tenant_isolation` RLS + guarded `GRANT … medicore_app`), same block as migration 0034 above. **App-level status sweep is NOT automatic:** renaming the enum is a compile error at every `eq(table.status, "uploaded")` / `=== "reviewed"` site (caught by typecheck — dashboard/reports services, DoctorDashboard) plus untyped string fixtures (seed). Grep the old literals before declaring done.

- **`IMAGING_STORAGE_DIR` + encrypted image files on a volume (2026-06-21)**: Uploaded X-ray/ultrasound images are written to `IMAGING_STORAGE_DIR` (default `./storage/imaging` in dev — gitignored; a named Docker volume `imaging_data` mounted into api+worker in prod) as **AES-256-GCM ciphertext** (kid/iv/tag persisted on the `imaging_attachments` row, not on disk; dev with no `FIELD_ENCRYPTION_KEY` stores plaintext + null envelope, mirroring field-level behavior). **The volume is NOT in the DB dump** — `docker-compose.prod.yml`'s backup container mounts it read-only and `tar`s it into `/backups` daily alongside the pg_dump (same retention). **Rule:** any new on-disk PHI store must (a) be gitignored, (b) join the backup set, and (c) be purged by `executeErasure` — the imaging files are hard-`unlink`ed post-commit (the row's iv/tag is what makes the leftover bytes useless, so deleting the file is the irreversible erasure). Never serve `IMAGING_STORAGE_DIR` via `express.static` — the only reader is the authenticated, doctor-scope-checked, audited `GET …/images/:attId` endpoint.

- **Migration 0034 — `inventory_transactions` stock-movement ledger (2026-06-17)**: New append-only table (UUID-v7 PK) — one row per quantity change (`delta` signed, `quantity_after` snapshot, `reason` enum `initial|restock|consumed|expired|adjustment`, `note`, `performed_by_id`, `created_at`). **A new clinic-bearing table must replicate the full tenant-isolation standard manually** — `db:generate` only emits the `CREATE TABLE`/FKs/index, NOT the RLS. The generated SQL was hand-appended with: `CHECK (clinic_id > 0)` (0014 standard), `ENABLE`+`FORCE ROW LEVEL SECURITY` + the **dormant** `tenant_isolation` policy (0015 standard — gate on `app.rls_enforce` + `nullif` guard, NOT a strict policy, or every `dbUnsafe` read returns zero rows per the F-P1-1 lesson below), and a guarded `GRANT … TO medicore_app` (0020 standard; wrapped in an `IF EXISTS pg_roles` DO-block so it no-ops on dev DBs that never created the role). 0020's `ALTER DEFAULT PRIVILEGES` also covers owner-created tables, but the explicit grant is belt-and-braces + self-documenting. The service writes ledger rows **inside the same `runInTenantContext` tx** as the inventory update so the movement and the new quantity commit atomically; `adjustInventoryStock` rejects a result < 0 so `delta == quantity_after - quantity_before` always holds. **Rule:** every new clinic-bearing table → copy this block (CHECK + dormant RLS + grant); add it to the integration-db tenant-isolation expectations if one enumerates tables.

- **Migration 0032 — `operation_status` gains `requested` (2026-06-16)**: `ALTER TYPE "operation_status" ADD VALUE 'requested' BEFORE 'scheduled'` for the surgery approval gate (doctor request → admin approves → scheduled). Pure enum-value add; the column default stays `scheduled` and the service sets `requested` explicitly only for doctor-created ops. **Caveat:** `ALTER TYPE … ADD VALUE` is fine inside drizzle-kit's migration transaction on PG 12+ **only because the new value is not USED in the same migration** — never combine an enum ADD VALUE with a statement that references the new value in one migration file (split them). Approval authority is enforced in `operations.service.updateOperation` (a `doctor` moving `requested`→`scheduled` → `ForbiddenError`), NOT at the route layer (the PATCH route still allows `doctor` for normal edits). **Note:** operation notifications reuse the `general` `notification_type` (the enum has no `operation_*` value, same call as rx→pharmacy) — if you want them filterable later, add enum values in a migration.

- **Migration 0031 — `images` (jsonb) + `order_group_id` on imaging/lab tables (2026-06-16)**: Adds `images jsonb` (nullable) to `xray_records` + `ultrasound_records`, `order_group_id text` (nullable) to `xray_records`/`ultrasound_records`/`lab_tests`, and a `(clinic_id, order_group_id)` index per table. All additive + nullable → safe `ADD COLUMN` on populated tables, no backfill. **`images` holds `[{url, fileName?, caption?}]`** — it is NOT field-encrypted (image URLs are references, like `image_url`, not PHI ciphertext); the cover stays mirrored in `image_url` for list thumbnails/back-compat. **`order_group_id` is a client-generated UUID** shared by rows created together in one multi-add submit (set only when >1 item); it is NOT a foreign key / parent table — it's a soft grouping tag for list badges + (future) combined print. The list `select` projections in `xray/ultrasound/lab.service.ts` had to be widened to return the new columns (explicit selects, not `select *`). **Rule:** if you later need billing-grade orders (one invoice line per order, accession numbers), promote `order_group_id` to a real `*_orders` parent table — don't overload this tag.

- **Migration 0030 — `mrn_seq` / `invoice_seq` are now schema-declared sequences, created by a migration (2026-06-15)**: These two sequences (consumed via raw `nextval()` in `generateMRN()` and billing) previously existed ONLY because the **dev seed** ran `CREATE SEQUENCE IF NOT EXISTS`. The seed is destructive (truncates all data) so it never runs in prod → a freshly-migrated prod DB had no sequence and the first patient registration / invoice would fail with `relation "mrn_seq" does not exist`. They are now declared as `pgSequence` in `lib/db/src/schema/sequences.ts` so `db:generate` tracks them. **The generated `0030_*.sql` was hand-edited to `CREATE SEQUENCE IF NOT EXISTS`** — every already-seeded environment (dev + anywhere the seed ran) already has them, and plain `CREATE SEQUENCE` would abort the migration there. This SQL-only edit does not touch the drizzle snapshot, so `migration-drift` stays clean (verified: post-apply `db:generate` reports "No schema changes"). **Lesson:** infrastructure objects used via raw SQL (`nextval`, custom functions, extensions) must be schema-declared or put in a migration — never created only by the seed, or they silently go missing on any unseeded environment. **Rule:** when a generated migration creates an object that may already exist from historical seeding, add `IF NOT EXISTS` (the snapshot is unaffected).

- **Migration 0029 — `patients.id_card_number` is `NOT NULL` + per-clinic UNIQUE (2026-06-15)**: Adds `id_card_number text NOT NULL` and `CREATE UNIQUE INDEX patient_clinic_idcard_uq ON patients (clinic_id, id_card_number)`. Because the column is `NOT NULL` with **no default**, the `ADD COLUMN` fails on a non-empty `patients` table — apply it only after the table is empty (the dev rollout truncated the 3 test patients first, owner-authorized, then reseeded). **For staging/prod with real patients you cannot truncate:** this migration must be reworked into a 3-step backfill (add nullable → backfill `id_card_number` for every existing row → `SET NOT NULL` + add the unique index), or it will abort. The field is **plaintext** (searchable + uniquely constrainable — an identifier like `mrn`/`phone`, deliberately not in `AUDIT_PHI_REDACT_FIELDS` / field-encryption). **Rule:** the per-clinic uniqueness is `(clinic_id, id_card_number)` — never a global unique on `id_card_number` alone (different clinics legitimately see the same national ID). Duplicate inserts surface as `ConflictError` (409) via the service pre-check, with the unique index as the DB backstop. Any new patient-insert path (tests, fixtures, importers) must supply `idCardNumber` or hit a 23502; all `*.integration-db.test.ts` fixtures were updated this pass — note the constraint-specific `expectDbReject` tests (clinic_id CHECK / NOT NULL) **require** a non-null `idCardNumber` so the *intended* constraint is the one that trips.

- **Migration 0027 — `clinic_id` has NO column default anymore; every insert MUST set `clinicId` (2026-06-07, F-P5-1 hardening)**: All 20 clinic-bearing tables previously declared `clinic_id integer NOT NULL DEFAULT 1`. That default silently mislabeled any insert that omitted `clinicId` as clinic 1 — correct by accident for the seed clinic, a cross-tenant data-integrity bug for any other tenant (it's what let `invoice_items` and `notifications` rows land on clinic 1 in F-P5-1). 0027 (`0027_mean_maddog.sql`, drizzle-generated) runs `ALTER TABLE … ALTER COLUMN clinic_id DROP DEFAULT` on all 20 (idempotent, metadata-only). **`clinicId` is now a required field in Drizzle's insert type** — omitting it is a compile error, and at runtime a NOT NULL violation (SQLSTATE 23502) instead of a silent mislabel. **Rule:** never re-add `.default(1)` (or any default) to a `clinic_id` column; pass `clinicId: req.user!.clinicId` on every insert (or `SYSTEM_CLINIC_ID` for genuinely tenant-less system/audit events — see `lib/audit.ts`). Tables that never had the default (`doctor_schedules`, `schedule_overrides`) and `clinic_invoice_counters` (clinic_id is PK) are unaffected. Regression guard: `clinic-id-check.integration-db.test.ts` (NOT-NULL rejection + a no-default symmetry test). **Lesson:** a "convenience" column default on a tenant key is a footgun — it converts a forgotten scope into silent cross-tenant mislabeling; prefer a required field so the compiler + DB both catch the omission.

- **A `FORCE`-RLS table with a NON-dormant policy makes every `dbUnsafe` reader return ZERO rows (2026-06-04, F-P1-1)**: Migration 0022 enabled `FORCE ROW LEVEL SECURITY` on `doctor_schedules`/`schedule_overrides` with a *strict* policy (`clinic_id = current_setting('app.clinic_id')::int`, no `app.rls_enforce` gate, no `nullif` guard). Outside a tenant context the GUC is unset → `clinic_id = NULL` → the policy matches nothing, so a bare-`db`/`dbUnsafe` read silently returns **zero rows** (not all rows). This broke booking: `schedule-validator.ts` read schedules via `dbUnsafe` and every appointment create/reschedule failed `409 "No schedule for this day"` — invisible to CI because only the rejection path was tested. **Rule:** every clinic-bearing table uses the **dormant 0015 policy** (`coalesce(current_setting('app.rls_enforce',true),'off')<>'on' OR clinic_id = nullif(current_setting('app.clinic_id',true),'')::int`) for both USING and WITH CHECK. Migration **0025** realigned 0022's two tables to that shape. If you ever need a stricter table, audit every `dbUnsafe` reader of it first. When a table is FORCE-RLS, reads must run inside `runInTenantContext` or use the dormant pattern.

- **Migration 0024 — break-glass read bypass GUC `app.break_glass_patient_ids` (2026-06-04, F-P2-1)**: The 0017 `doctor_scope` RESTRICTIVE policy hid the 5 doctor-bound clinical tables from a doctor even under an active break-glass session (emergency access returned demographics only). 0024 extends the `doctor_scope` USING clause with `OR patient_id = ANY(string_to_array(nullif(current_setting('app.break_glass_patient_ids',true),''),',')::int[])`. **WITH CHECK is NOT relaxed** → break-glass is read-only. `runInTenantContext(user, fn, { breakGlassPatientIds })` sets the GUC (sanitized to positive ints); `break-glass.service.getActiveBreakGlassPatientIds()` + `scope.ts` (`getDoctorListScope`, break-glass-aware `assertMedicalRecordInScope`) drive it; all 5 clinical services pass it on list + getById. **Adding a new doctor-scoped clinical table?** add it to the 0017/0024 policy arrays AND wire its service like the existing five.

- **`executeErasure` must scrub EVERY PHI-bearing table (2026-06-04, F-P3-1)**: Previously it scrubbed only `patients` + `medical_records`; prescriptions were soft-deleted with the encrypted `medications` ciphertext retained, and `lab_tests`/`xray_records`/`ultrasound_records` (plaintext PHI) were untouched — while the audit logged `erasedEntities: [...prescriptions]` (overstated). It now scrubs all clinical tables in one transaction and derives `erasedCounts` from `.returning()` counts. **When you add a new PHI-bearing table, extend `executeErasure` (services/erasure.service.ts) and the erasure integration test** — there is no automatic coverage.

- **Audit integrity must be VERIFIED on a schedule, not just RECORDED (2026-06-05, F-P4-1/2)**: The daily cron previously only called `recordDailyIntegrity` (stores hashes). `verifyIntegrity` — the only thing that re-derives and sets `status='mismatch'`/increments the alert counter — ran only in tests, so `AuditIntegrityMismatch` could never fire and the restore-drill `checkAuditIntegrity` (which only `SELECT`s `status='mismatch'`) always passed. The daily cron now also runs `verifyRecentIntegrity` (rolling re-derivation, env `AUDIT_VERIFY_WINDOW_DAYS` default 7) + `verifyChainLinkage` (asserts each `prevHash` == prior calendar day's `rootHash`). **Don't conflate recording with verifying** — recording alone is not a tamper-evidence control.

- **Migration 0026 — `audit_logs` is append-only for `medicore_app` (2026-06-05, F-P4-3)**: Revokes `UPDATE, DELETE` on `audit_logs` (parent + all existing partitions) from `medicore_app`; it keeps `SELECT, INSERT` (all the code needs). **Caveat:** 0020's `ALTER DEFAULT PRIVILEGES` re-grants UPDATE/DELETE on tables created later by the owner, so a **newly-created audit partition re-acquires the grant** — re-run the 0026 REVOKE on each new partition (per the `AuditPartitionLow` runbook step).

- **Audit before/after must go through `auditSnapshot()` — never pass raw rows (2026-06-02, compliance UIs)**: `logAudit(req, action, type, id, details?, beforeState?, afterState?)` supports change-history snapshots. Always wrap rows: `auditSnapshot(beforeRow)` / `auditSnapshot(afterRow)` (helper in db-free `lib/audit-snapshot.ts`, re-exported by `lib/audit.ts`). It redacts the five field-encrypted columns (`diagnosis`, `vitals`, `medications`, `allergies`, `emergencyContact`) to `"[redacted]"` and drops noise columns (`createdAt`/`updatedAt`/`deletedAt`/`clinicId`/`searchVector`/`password*`). **Why:** passing a raw row would either (a) dump rotating-IV ciphertext that always "differs" and is unreadable, or (b) — if decrypted first — create a *second cleartext-PHI store* in `audit_logs`, defeating field encryption. `medical-records.service.ts` previously passed raw `existing`/`record` (bug class (a)) — fixed in this pass. Put changed field *names* in `details.fields` using the patch keys, NOT a ciphertext compare (encrypted fields false-positive every write). Making encrypted-field *values* visible in change-history is a deliberate PHI-surface decision — change `AUDIT_PHI_REDACT_FIELDS`, never ad hoc.

- **OpenAPI `AuditLog.entityId` is `string`, not `integer` (2026-06-02, compliance UIs)**: The spec previously typed `entityId` as `integer nullable`, but the DB column is `text` (holds UUIDv7 entity IDs from newer tables). Fixed to `string nullable`. Also added `beforeState`/`afterState` to the `AuditLog` schema and surfaced the pre-existing `GET /audit-logs/entity/{entityType}/{entityId}` route in the spec (operationId `getAuditLogsByEntity`). Non-breaking (the column was already `text`); regenerate clients with `pnpm --filter @workspace/api-spec run codegen` after pulling.

- **`translations` is now a named export from `hooks/i18n.tsx` (2026-06-02, F-03)**: The `const translations` object was made `export const translations` so the `i18n.test.ts` key-parity test can import it directly. If you have a barrel file or re-export layer that previously only exported `I18nProvider`, `useI18n`, and `I18nContextType`, add `translations` to it. The object's type (`typeof translations`) is unchanged — the `t()` function signature (`key: keyof typeof translations.en`) still holds. **Do not add new translation keys to only one language** — the `i18n.test.ts` parity guard (`EN keys ≡ AR keys`) will fail the `frontend-test` CI job immediately.

- **Migration 0020 creates `medicore_app` role — api/worker must switch DATABASE_URL (2026-06-02, F-01 fix)**: `0020_create_app_role.sql` creates the `medicore_app` role as NOSUPERUSER NOBYPASSRLS. The migrate container reads `./secrets/app_db_password` and calls `ALTER ROLE medicore_app LOGIN PASSWORD '...'` after migrations complete, then runs a smoke gate. api and worker now connect as `medicore_app` (not the bootstrap superuser). **Before deploying**: create `./secrets/app_db_password` (`openssl rand -base64 48 | tr -d '\n' > ./secrets/app_db_password`, `chmod 600`). The compose smoke gate will fail if this file is missing or the GRANT was not applied. **Rollback caveat**: rolling back past 0020 leaves the `medicore_app` role in Postgres but removes the GRANT. If you must roll back, manually run `DROP ROLE medicore_app` as the superuser AND switch the api/worker DATABASE_URL back to the bootstrap superuser before restarting — otherwise containers fail to connect. This migration is one-way; treat any rollback as a SEV-1 change. See RUNBOOK §0 and ADR-008-app-db-role.md.

- **Services now use `dbUnsafe` for non-tenant DB access (2026-06-02)**: The `@workspace/db` package exports `dbUnsafe` (alias of `db`). Services that legitimately bypass tenant context (pre-auth, tables without clinicId) must import `dbUnsafe` not `db`. The ESLint rule in `eslint.config.mjs` blocks bare `db` imports in `src/services/**` at lint time. If you add a new service that uses the raw DB client for non-tenant reasons: (1) import `dbUnsafe`, (2) add a one-line justification comment, (3) run `pnpm --filter @workspace/api-server run lint` to verify. If your use case is clinic-bearing, use `runInTenantContext(req.user!, async (tx) => …)` instead — never import `db` directly in a service.

- **Arabic clinical columns are in migration `0019_old_makkari.sql` — all nullable (2026-05-31, Phase 6)**: The migration adds `locale text NOT NULL DEFAULT 'en'` and `timezone text NOT NULL DEFAULT 'Europe/Istanbul'` to `clinics`, and `*_ar text` columns to `medical_records`, `prescriptions`, `lab_tests`, `xray_records`, `ultrasound_records`, and `services_catalog`. All Arabic columns are nullable — no NOT NULL constraint, no default. Apply before deploying the Phase 6 api binary: `pnpm --filter @workspace/db run db:migrate`. If you have existing rows the `ALTER TABLE ADD COLUMN` is safe with no backfill needed. **Never make the Arabic columns NOT NULL** — the bilingual design intentionally allows unilingual records. Enforcement belongs in UI labels only.

- **Doctor analytics does NOT cache — `logRead` is called on every hit (2026-05-31, Phase 6)**: `getDoctorAnalytics` and `listDoctorAnalytics` call `void logRead(req, "ANALYTICS", ...)` on every request. Do NOT wrap either function in `runtime.cache.getOrSet()` — caching skips the audit log (HIPAA gap) and would persist aggregated PHI in Redis. The analytics queries are already fast (no N+1 — all appointment + lab + xray data fetched in two round trips, revenue in one query per doctor). If performance becomes an issue, consider a separate read replica (see ROADMAP "Read replicas") not a cache.

- **`xray.service.ts` / `ultrasound.service.ts` update mutations accept `findingsAr` / `impressionAr` as top-level body fields (2026-05-31, Phase 6)**: These fields are not stored in their own columns — `findingsAr` and `impressionAr` for xray/ultrasound are passed through to the frontend via `reportAr` (encrypted). The frontend reads them back from the `reportAr` column (parsed from JSON if structured, or plain text). If the API spec is updated in a future pass to surface these as first-class fields, the service must parse `report_ar` accordingly. For now, the frontend stores them alongside English findings in `report` as a structured JSON `{ v: 1, findings, impression }` and separately passes `findingsAr` / `impressionAr` to the update mutation as `any`-typed extras — this works because the service accepts the full body and maps whichever columns are present.

- **`docker-compose.prod.yml` gains four containers + two secrets + five volumes (2026-05-31, Phase 4 Operational Hardening)**: New services `prometheus`, `alertmanager`, `grafana`, `backup`. New secrets `grafana_password` and `backup_ssh_key` — both must exist (mode 0600) at `./secrets/` before `up`. New volumes `prometheus_data`, `alertmanager_data`, `grafana_data`, `backup_data`, `backup_metrics` — mount host paths or NFS for `backup_data` to survive container lifetime. New required `.env` vars (compose rejects missing `:?` placeholders): `SMTP_SMARTHOST`, `SMTP_FROM`, `SMTP_AUTH_USER`, `SMTP_AUTH_PASS`, `ALERT_EMAIL_TO`, `BACKUP_GPG_RECIPIENT`, `BACKUP_RSYNC_TARGET`. If you are pulling this branch into an existing prod deployment, **add these env vars and secret files before `docker compose up -d`** or compose parsing will fail before any service starts.

- **API/worker now use `image:` with `build:` fallback (2026-05-31, Phase 4)**: The `api` and `worker` services resolve their image from `${API_IMAGE:-medicore-api:latest}` (worker also falls back to `WORKER_IMAGE`). Pre-Phase-4 deployments rebuilt from source on every `up -d`; the new pattern lets you `up -d --no-build` after a CI build pushes a tagged image. If your existing CI does not push images, set `API_IMAGE=medicore-api:latest` in `.env` and keep using `up -d --build`. **There is no `down` migration**: rolling back a deploy reverts code only; if the bad release shipped a destructive Drizzle migration (dropped column, narrowed type, RLS policy that breaks reads), the choices are roll-forward-hotfix or restore-from-backup. See [RUNBOOK.md §10.2](RUNBOOK.md).

- **Grafana is intentionally not exposed via Caddy (2026-05-31, Phase 4)**: The `grafana` container binds `127.0.0.1:3000` on the host and attaches to `backend` only — no `frontend` network, no `handle_path /grafana/*` in `caddy/Caddyfile`. This was an explicit operator decision: the app surface stays minimal on the internet, admin tooling reached via `ssh -L 3000:localhost:3000 deploy@host`. If you later expose Grafana publicly, add TLS + auth in front and revisit the `GF_SERVER_ROOT_URL` env — the current config assumes localhost access.

- **Alertmanager email config uses env-var interpolation, not file secrets (2026-05-31, Phase 4)**: SMTP credentials live in the alertmanager container's `environment:` block, not in `./secrets/`. This is a deliberate trade-off — Alertmanager's YAML supports `${VAR}` interpolation but not file-based secrets without a sidecar template renderer. The result: `docker inspect alertmanager` exposes `SMTP_AUTH_PASS`. If your SMTP provider supports app-specific tokens (Gmail app password, SES SMTP creds), use one. Do NOT reuse the same SMTP password elsewhere.

- **Backup container shells out to `apk add` at startup (2026-05-31, Phase 4)**: `gnupg`, `openssh-client`, `rsync` are not in the base Dockerfile build target — the backup entrypoint installs them on first run (and on every restart). This is intentional: the api/worker runtime images stay minimal (no GPG/SSH/rsync in the attack surface of the request-handling containers). If you ever change the backup container to share the runtime image, you must also add these packages to the Dockerfile or backup will fail with "command not found". Network egress for `apk` requires the `backend` network keep `internal: false` (current default).

- **`runtime.scopeCache` is now part of `/api/health` readiness (2026-05-31, Phase 4)**: `checkReadiness()` performs `SET health:ping 1 EX 5` + `GET` against `runtime.scopeCache`. - **JWT_SECRET deduplication (2026-05-24)**: `JWT_SECRET` was independently declared in both `lib/auth.ts` (with production guard) and `lib/policy.ts` (without guard). Extracted to `lib/jwt-secret.ts` — single declaration, both files import from it. When touching auth crypto, always import from `jwt-secret.ts`, never redeclare.

- **ROLE_TTL / COOKIE_TTL_MS deduplication (2026-05-24)**: Per-role TTL existed as two independent `Record<string, ...>` maps — `ROLE_TTL` (jose TTL strings) in `lib/auth.ts` and `COOKIE_TTL_MS` (ms numbers) in `routes/auth.ts`. Both moved to `lib/auth-constants.ts`. Drift between the two caused potential silent broken-auth (JWT expired before cookie, or cookie expired before JWT). Any new role must be added to **both** maps in `auth-constants.ts`.

- **Cron patient recall deleted (2026-05-25)**: The daily 08:00 recall cron was a no-op — it ran a complex SQL query and logged the count, but the `db.insert(notificationsTable)` call was commented out. Deleted entirely. Do not re-add until SMS/WhatsApp (Phase 7) provides a delivery channel.

- **Phase 6 multi-tenancy reverted (2026-05-25)**: UUID PKs, `clinics` table, `clinic_id` FK on all PHI tables, and `clinicId` in JWT claims were partially implemented then rolled back at Mike's explicit request. Only cursor pagination and Redis doctor-scope cache were kept. Do not re-introduce `clinic_id` or UUID PKs until multi-tenancy is explicitly re-scoped. Integer serial PKs remain throughout.

- **Offset pagination → cursor pagination (2026-05-25)**: All 7 list endpoints (`patients`, `appointments`, `lab`, `xray`, `ultrasound`, `prescriptions`, `medical-records`) changed from `?limit&offset` to `?limit&cursor`. `cursor` is the integer `id` of the last record in the previous page. Response shape is now `{ data, nextCursor }` (patients: `{ patients, total, nextCursor }`). `ORDER BY id DESC` replaces `ORDER BY createdAt DESC` for stable pagination. `nextCursor: null` means last page. Frontend list pages have not been updated to use `useInfiniteQuery` — they still work (no cursor = first page) but load-more pagination is not wired.

- **VACUUM removed from app layer (2026-05-25)**: `cron.ts` had a nightly `VACUUM ANALYZE` run via `db.execute(sql\`VACUUM ANALYZE;\`)`. This is an autovacuum concern, not an application concern; it also cannot run inside a transaction. Configure PostgreSQL `autovacuum_vacuum_scale_factor` / `autovacuum_analyze_scale_factor` instead. Never call VACUUM from application code.

- **Cron now routes through validateTransition (2026-05-25)**: The no-show auto-transition used a direct `db.update` that bypassed the state machine entirely. Now calls `validateTransition("no_show", "scheduled", "system")` first — if the state machine rejects the path (e.g. someone removes `no_show` from the allowed transitions), the cron logs an error and aborts rather than silently drifting out of sync. "system" is a new bypass actor in `validateTransition`, alongside `super_admin`; it skips role checks but not source-state checks.

- **Audit before/after state columns (2026-05-25)**: Previously UPDATE audit entries stored `{ before: ..., after: ... }` in the unstructured `details` JSONB. Added dedicated `before_state` / `after_state` JSONB columns to `audit_logs`. `logAudit` now accepts them as the 6th and 7th arguments. Do not embed before/after diffs inside `details` — use the dedicated columns so compliance queries can target them with JSON path operators.

- **ALLOWED_ORIGINS CORS env var (2026-05-25)**: `app.ts` CORS now reads `ALLOWED_ORIGINS` (comma-separated) in addition to `REPLIT_DOMAINS`. Each value is treated as a literal origin string (regex-escaped, exact match). Use this to allow the frontend when not deploying on Replit. Both env vars are additive; neither replaces the other.

- **PHI field-level encryption (2026-05-25)**: AES-256-GCM applied to `diagnosis`, `vitals` (medical_records), `medications` (prescriptions), `allergies`, `emergencyContact` (patients). Key = `FIELD_ENCRYPTION_KEY` env var (64 hex chars). Envelope format: `enc:v1:<iv_hex>:<tag_hex>:<data_base64>`. Module init throws in production if key absent; logs a warning in dev and runs unencrypted. Backward-compat: values not prefixed `enc:v1:` are returned as-is on decrypt — safe for existing dev data. JSONB columns (vitals, medications) are stored as encrypted string literals — Drizzle returns them as `string`; detect with `isEncrypted()` before calling `decryptJson()`. Never remove backward-compat path until all rows in prod have been re-encrypted with a migration script.

- **Treatment consent enforcement (2026-05-25)**: `hasActiveConsent(patientId, "treatment")` must return `true` before `createMedicalRecord` or `createPrescription` succeeds. Throws `ConsentRequiredError` (HTTP 422, error code 3010) otherwise. The check is at the service layer — routes need no change. When writing new services that create PHI, follow this pattern.

- **Right-to-erasure irreversibility (2026-05-25)**: `executeErasure` runs in a DB transaction and replaces PHI with `[ERASED]` / `1900-01-01` constants. There is no undo path. The audit log entry is written *outside* the transaction (immutable, survives rollback). Erasure requests must be `approved` before execution; only `super_admin` can execute. Per ADR-005: hard deletion of rows is prohibited — audit linkage must be retained. Future compliance queries should join on `erasure_requests.patientId` to detect anonymized subjects.

- **Break-glass SSE alert (2026-05-25)**: `activateBreakGlass` sends an SSE event to every `compliance_officer` via `emitToUser` for each officer's userId. If no compliance officers exist in the DB, the activation still succeeds (no error thrown). `alertSentAt` is set in the `break_glass_sessions` row only after all SSE calls complete. PHI must NOT flow through SSE payloads — the alert payload carries `sessionId`, `userId`, `patientId`, `justification`, and `activatedAt` only.

- **Docker build strategy (2026-05-25)**: Multi-stage `Dockerfile` for the api-server — deps stage installs pnpm workspace, build stage runs esbuild, runtime stage copies only `dist/*.mjs` + the `bcrypt` native addon (the only externalized non-Node runtime dep). `Dockerfile.clinic` builds the React SPA with Vite and copies static output into an `nginx:1.27-alpine` image. `nginx.conf` proxies `/api/*` to the `api` service with SSE buffering disabled, blocks `/metrics` at the edge, and adds a 1-year cache header for hashed assets. `docker-compose.yml` runs a one-shot `migrate` init container (reusing the `build` stage) to apply pending migrations before the API boots.
