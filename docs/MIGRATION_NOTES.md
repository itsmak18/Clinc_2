# Migration Notes — Lessons Learned / Deprecated Approaches

- **`clinicId` is now required on `AuthUser` / `AuthRequest.user` (2026-05-28)**: `AuthUser.clinicId: number` and `AuthRequest.user.clinicId: number` are required fields. The policy kernel fills the value with `payload.clinicId ?? 1` for backward compat with existing JWTs. **Every PHI service query MUST include `eq(table.clinicId, req.user!.clinicId)` in its conditions array.** Missing this filter means any authenticated user of another clinic can read any PHI row from the same table. Test mocks that supply `req.user` via `as unknown as AuthRequest` or `as any` do not need updating (casts bypass the type check), but any mock that constructs the user object literally must now include `clinicId`. **`usersTable` gains `clinic_id integer NOT NULL DEFAULT 1`** — apply migration `0008_acoustic_cassandra_nova.sql` before deploying. Existing rows in `users`, `operations`, `inventory` populate with value `1`. `TokenPayload.clinicId` is optional (old tokens without the claim still verify; kernel fills `?? 1`). Once per-role TTLs rotate (max 4h), every active JWT carries the claim.

- **SSE `event: shutdown` is replaced by `event: reconnect` with jitter (2026-05-28)**: `closeAllSSEClients()` no longer sends `event: shutdown\ndata: {"reason":"server_shutdown"}`. It now sends `retry: <jitterMs>\nevent: reconnect\ndata: {"reason":"server_draining","retryAfter":<jitterMs>}\n\n` where jitter is randomized per connection (5 000–15 000 ms). Frontend `use-notifications-stream.ts` handles the `reconnect` event with a `setTimeout(connect, retryAfter)` delay. Any external SSE client or test that asserts `event: shutdown` must be updated. The `SHUTDOWN_TIMEOUT_MS` default has been raised from 25 000 to 30 000 ms; ensure the host process manager gives at least 35s before SIGKILL (`stop_grace_period: 35s` is now in both compose files). `SSE_DRAIN_MS` env var (default 10 000 ms) controls how long existing connections are held open before the reconnect event is sent — set to 0 in test environments.

- **Erasure restores require re-anonymization within the blackout window (2026-05-28)**: `executeErasure()` now sets `erasure_blackout_until = executedAt + BACKUP_RETENTION_DAYS` on the `erasure_requests` row. Any backup produced before that timestamp still contains pre-erasure PHI. If you restore from such a backup, you MUST re-apply the anonymization SQL for each affected patient before promoting the restore — see RUNBOOK §2.2 step 5. `backup-verify.mjs --restore` enforces this automatically (fails the drill if active blackouts are detected). Apply migration `0007_wide_zarda.sql` with `pnpm --filter @workspace/db run db:migrate` — instant metadata-only `ALTER TABLE` change.

- **Audit write is now outbox-based — fire-and-forget pattern retired (2026-05-28)**: `logAudit()` no longer writes directly to `audit_logs`. It now writes to `audit_outbox` (an unindexed, FK-free queue table). A background drain worker (`drainAuditOutbox()`, called every 5 s from `startAuditDrain()` in `cron.ts`) transfers rows to `audit_logs` with exponential backoff (5 s → 30 s → 2 min → 10 min) and up to 5 attempts. Rows exhausted after 5 attempts are counted in `audit_log_write_failures_total` and logged at `audit_outbox_row_exhausted`. **Test mocks that stub `@workspace/db`** must now include `auditOutboxTable: {}` — previously `auditLogsTable` was the only table `logAudit()` touched. Any new test file that mounts the Express app (and therefore triggers `logAudit()` calls) must add `auditOutboxTable` to its DB mock. The Prometheus metric `audit_log_write_failures_total` now means **permanent loss** (exhausted rows), not temporary failures. Prometheus alert for `audit_outbox_drain_failed` is more important than the counter. **Apply migration `0006_odd_machine_man.sql`** before deploying: `pnpm --filter @workspace/db run db:migrate`.

- **`invoices.items` JSONB column dropped — `invoice_items` is now the sole source of truth (2026-05-28)**: The dual-write pattern (write to both JSONB column and normalized `invoice_items` table) has been eliminated. The column is removed from `invoicesTable` in `billing.ts` and from the DB via migration `0005_charming_psynapse.sql`. Apply before deploying the new api binary: `pnpm --filter @workspace/db run db:migrate`. The API response shape is unchanged (`items: InvoiceItem[]` is still returned from all billing endpoints — now sourced via a normalized join instead of the JSONB read). **Never add `items: jsonb(...)` back to `invoicesTable`** — any future line-item feature belongs in `invoice_items`. The `itemsSchema` Zod validator in `lib/jsonb-schemas.ts` is retained for input validation in `createInvoice()` — do not remove it even though the JSONB column is gone.

- **JWT is now EdDSA asymmetric — HS256 is gone (2026-05-28)**: `lib/jwt-secret.ts` was completely rewritten. JWT signing now uses an Ed25519 key pair (`JWT_PRIVATE_KEY` PKCS8 PEM + `JWT_PUBLIC_KEY` SPKI PEM) via `jose`. The algorithm header changed from `{ alg: "HS256" }` to `{ alg: "EdDSA", kid: "<kid>" }`. All existing HS256 sessions are invalidated on deploy — users will get a 401 and must re-login. This is a one-time migration cost. **`SESSION_SECRET` is no longer the JWT signing key** — it is now the HMAC key for device fingerprinting (`lib/device-fingerprint.ts`) only. Do not use `SESSION_SECRET` for JWT operations. The `JWT_SECRET: Uint8Array` export from `lib/jwt-secret.ts` is preserved for `device-fingerprint.ts` backward compat — do not remove it. The public key set is advertised at `GET /api/.well-known/jwks.json` (Cache-Control: public, max-age=3600). Key rotation overlap: set `JWT_PREV_PUBLIC_KEY` + `JWT_PREV_KID` in the entrypoint to advertise both old and new public keys during rotation — old tokens verify until they expire naturally. See `SECURITY.md §"JWT key rotation"` for the 6-step quarterly rotation procedure. **Deploy action required**: create `./secrets/jwt_private_key` + `./secrets/jwt_public_key` (mode 0600) before next prod restart. Atomic generator: see `secrets/README.md`.

- **Field-encryption envelope is now KID-aware (2026-05-27)**: `lib/field-encryption.ts` now writes `enc:v2:<kid>:<iv>:<tag>:<data>`. Legacy `enc:v1:<iv>:<tag>:<data>` envelopes are still decrypted (via `kid="1"` key) but new writes always produce `enc:v2:`. `FIELD_ENCRYPTION_KEY` feeds `kid="1"`. Optional `FIELD_ENCRYPTION_KEY_NEXT` feeds `kid="2"` during rotation. `FIELD_ENCRYPTION_KEY_WRITE_KID` (default `"1"`) controls which kid new writes use. **Never delete `FIELD_ENCRYPTION_KEY` while `enc:v1:` or `enc:v2:1:` envelopes exist in the DB** — the module throws on decrypt, data is effectively unreadable. See `SECURITY.md` for the six-step rotation procedure.

- **PHI-decryption-capable secrets are now file-mounted in production (2026-05-27)**: `SESSION_SECRET`, `FIELD_ENCRYPTION_KEY`, and `METRICS_TOKEN` were moved from the `environment:` block of `docker-compose.prod.yml` to Docker secrets (`/run/secrets/*`). **Before the next `docker compose -f docker-compose.prod.yml up -d`** you must create all three files at `./secrets/{session_secret,field_encryption_key,metrics_token}` with `chmod 600`. The entrypoint uses `test -s` to fail-close if any file is missing or empty — the container will not start. `JWT_SECRET` env var is fully removed (dead code — `lib/jwt-secret.ts` reads `SESSION_SECRET` exclusively). `REDIS_PASSWORD` is still env-passed (interpolated into `REDIS_URL` at compose parse time).

- **Express trust proxy is now set (2026-05-27)**: `app.set("trust proxy", "loopback, linklocal, uniquelocal")` was added to `app.ts` before all middleware. Behind Caddy on the docker bridge network `req.ip` previously resolved to the Caddy container IP, causing every rate-limit key and audit IP field to collapse to one identity. This is now correct. The regression test in `trust-proxy.test.ts` pins the setting — do not remove it or change the trust string without also updating those tests and verifying the rate-limiter works correctly with multi-IP XFF headers.

- **Cursor pagination is now complete end-to-end (2026-05-27)**: Backend list endpoints moved to cursor in Phase 6. Frontend call sites were still passing `offset: 0`. All 12 call sites (11 pages + `components/CommandPalette.tsx`) have been migrated. OpenAPI spec updated: `offset` → `cursor` on `/patients` and `/appointments`; new `PaginatedAppointments` schema. A CI grep guard in `ci.yml` now blocks `offset:N` params in `artifacts/clinic/src/pages/` and `components/` (except `AuditLog.tsx`). **Do not pass `offset:` to any generated hook** — use the cursor-based params or leave the param unset (returns first page). `AuditLog.tsx` is the only intentional offset survivor and is explicitly excluded from the CI guard.

- **`Appointments.tsx` and `DoctorDashboard.tsx` runtime bug fixed (2026-05-27)**: The OpenAPI spec previously declared `GET /appointments` response as `array of Appointment`. Backend actually returns `{ data: Appointment[], nextCursor: integer | null }`. TypeScript believed the spec; calling `.map()` on the response object would throw `TypeError` at runtime. The pagination spec migration corrected this — both pages now destructure `.data` from the response. Symptom in the wild: "Appointments list always empty" or "Recent patients panel never populates".

- **`pharmacist` can now read prescriptions (2026-05-27)**: `routes/prescriptions.ts` `GET /prescriptions` and `GET /prescriptions/:prescriptionId` were missing `pharmacist` from their `requireRole(...)` arrays. Pharmacists were being redirected to `/prescriptions` on login (their landing page) and immediately receiving 403. Fixed. The route-access contract test (`route-access.contract.test.ts`) now pins this invariant on every PR.

- **Bayan port complete — Phase 4 + 5 (2026-05-27)**: All 28 existing pages reskinned to Bayan classes; zero legacy theme tokens (`text-muted-foreground`, `bg-card`, `bg-primary`, `text-destructive`, `border-border`, `text-foreground`) remain in `src/pages/**`. 5 net-new pages added: `DoctorConsult.tsx` (tabbed EHR with `?p=<id>` deep-link via `useCurrentPatientId`), `DoctorOrders.tsx`, `DoctorInbox.tsx`, `NurseVitals.tsx`, `FrontDeskCheckin.tsx`. 6 new routes: `/today`, `/consult`, `/orders`, `/inbox`, `/checkin`, `/vitals`. `getLandingRoute` now sends doctor → `/today` (was `/dashboard`), front_desk → `/checkin` (was `/appointments`). Per-route ErrorBoundary (`RouteErrorReset` keyed by `useLocation`) so errors clear on navigation. Global `:focus-visible` outline rule in `index.css` covers all interactive elements — no need to add `focus-visible:*` Tailwind classes per-button.

- **`.btn-outline` was undefined but referenced (fixed 2026-05-27)**: Multiple pages used `className="btn btn-outline"` but the CSS class had no definition — buttons fell back to base `.btn` styling. Class is now defined in `index.css` (transparent background, line border, surface-2 hover). When adding new button variants, define the CSS rule before relying on it in JSX.

- **Bayan design port replaces the old shadcn dark-sidebar theme (2026-05-26)**: `index.css` `:root` + `.dark` blocks have been completely replaced with Bayan's mint/sage editorial token system. Old HSL variables (`--background: 222.2 84% 4.9%` etc.) no longer exist. All color references in the codebase MUST use the new CSS vars (`var(--ink)`, `var(--teal-500)`, etc.) or Tailwind semantic tokens (`text-foreground`, `bg-background`) that now map to the new vars via `@theme inline`. Hardcoded HSL values in any page or component will no longer match the design.

- **`Layout.tsx` sidebar color scheme changed (2026-05-26)**: The old layout used `bg-sidebar` (dark navy) with `text-sidebar-foreground` (white text). The new layout uses `var(--bg)` (light surface) with `var(--ink)` (dark text). Any component that previously hardcoded `text-sidebar-foreground` or `bg-sidebar` for nav item styles will need to be updated to `.nav-item` CSS class or direct use of `var(--ink-soft)`.

- **`nav-item` / `is-active` CSS classes replace shadcn Button-based nav (2026-05-26)**: Nav items now use `.nav-item` + `.is-active` CSS classes (defined in `index.css`) instead of shadcn `<Button variant="ghost">` with conditional `bg-sidebar-primary`. This applies to the sidebar navigation; do not use Button for nav items.

- **Directional Tailwind → logical properties (2026-05-26)**: All `ml-*`, `mr-*`, `pl-*`, `pr-*`, `text-left`, `text-right`, `border-l-*`, `border-r-*` in custom pages/components have been replaced with logical equivalents (`ms-*`, `me-*`, `ps-*`, `pe-*`, `text-start`, `text-end`, `border-s-*`, `border-e-*`). New code must use logical properties to ensure correct RTL rendering. Exception: shadcn/ui primitive files in `components/ui/` are not modified.

- **Phase 2 device-trust replaces TOTP MFA (2026-05-25)**: MFA was fully removed earlier; the auth-hardening compensating control is now **device-trust + email verification on new devices**, not TOTP. Auditors will expect §2.4 lockout-on-rejection and §2.7 step-up to be ironclad. ASN/country are NOT in the device fingerprint (cellular handoff would flip them on every login) — they are risk signals only. Fingerprint is HMAC'd with the server secret salted by `user_id` so DB leaks cannot correlate the same browser across users.

- **Phase 2 kill-switch is scaffolding, not architecture (2026-05-25)**: Every Phase 2 codepath sits behind `isPhase2Enabled()`. This is intentional for incremental rollout, but the off-path bit-rots if not exercised. CI MUST run the test suite with the flag both on and off, or delete the flag within ~30 days of production enablement (see ROADMAP Phase 2.11). A long-lived flag becomes a downgrade-attack surface: anyone with env-var write access can disable auth-hardening without code review.

- **`pending_verification` response is NOT the canonical error envelope (2026-05-25)**: `POST /auth/login` returns HTTP 202 `{ status, message }` on new-device privileged-role block — the same generic shape as `POST /auth/forgot-password`. This is deliberate (no enumeration oracle). Adding `error_code`/`error_name` would leak the existence/non-existence of the account.

- **Verification token fingerprint binding requires a 2-step consume (2026-05-25)**: The route layer cannot compute the fingerprint until it knows the `user_id`, but it doesn't know `user_id` until the token is decoded. Solution: `peekToken(rawToken)` looks up by `token_hash` without consuming → derive fingerprint with the known `user_id` → `consumeVerificationToken()` atomically locks. The "wasn't me" path bypasses fingerprint check (`bypassFingerprint: true`) because the rightful owner may click from any device.

- **JWT in localStorage (C-01, removed)**: Token was stored as `clinic_token` in `localStorage`, sent via `Authorization: Bearer`. Replaced with HttpOnly SameSite=Strict cookie set by `POST /auth/login`. Never reintroduce localStorage for auth. Cookie max-age matches per-role JWT TTL (15m–4h), NOT a flat 8h.

- **SSE auth via `?token=` query param (removed)**: SSE now uses `new EventSource(url, { withCredentials: true })` — the HttpOnly cookie is sent automatically.

- **Raw `fetch()` without CSRF header**: Orval-generated `customFetch` attaches `X-CSRF-Token` automatically. Any hand-written `fetch()` to a mutation endpoint must read `_csrf` from `document.cookie` and set `X-CSRF-Token`. Failure silently breaks server-side logout revocation (the server rejects with 403 which callers may swallow).

- **`app.use("/api", middleware)` path stripping**: Express strips the mount prefix from `req.path` inside the mounted middleware. So a middleware mounted at `/api` sees `/auth/login`, not `/api/auth/login`. The v7 kernel is method-gated (not path-gated) to avoid this pattern entirely — no `CSRF_EXEMPT_PATHS` list.

- **CSRF middleware → v7 kernel**: `middlewares/csrf.ts` is deleted. CSRF now runs inside `evaluate()` in `lib/policy.ts` for mutation methods. The unit test suite is `tests/policy.unit.test.ts` (25 tests covering every kernel branch including CSRF). There is no `csrf.test.ts`.

- **`verifyToken` fail-open (fixed)**: Catch block previously did `console.warn` + returned the token. Now throws `"Token verification unavailable"`. Revocation store errors are fail-closed.

- **`logout()` without server-side revocation (fixed)**: `POST /auth/logout` calls `revokeAllTokensForUser(userId)` before clearing the cookie. Without this, captured JWTs survive for the full role TTL after logout.

- **`LoginResponse` schema drift (fixed)**: After moving the JWT to a cookie, `openapi.yaml` still had `token: string` as required. Always update `openapi.yaml` first when migrating auth approaches, then run codegen and verify generated types.

- **Orval `api-zod` barrel export (Windows)**: Orval `split` mode writes an invalid barrel on Windows (git-bash interprets `\\n` literally). After codegen fails: `printf "export * from './generated/api';\n" > lib/api-zod/src/index.ts`, then run `pnpm -w run typecheck:libs` separately. The full codegen script will not succeed end-to-end on Windows.

- **MFA removed (2026-05-18)**: TOTP two-step login was fully implemented (otplib, AES-256-GCM encrypted secrets, recovery codes, mfa_sessions table, challenge routes) then **completely removed** to restore single-step login. The `users` table has no MFA columns. No `mfa_sessions` table exists. No MFA routes exist. The `/mfa-setup` reference in `route-access.ts` is dead code (safe to remove). Do not implement MFA features until explicitly re-scoped.

- **JWT_SECRET deduplication (2026-05-24)**: `JWT_SECRET` was independently declared in both `lib/auth.ts` (with production guard) and `lib/policy.ts` (without guard). Extracted to `lib/jwt-secret.ts` — single declaration, both files import from it. When touching auth crypto, always import from `jwt-secret.ts`, never redeclare.

- **ROLE_TTL / COOKIE_TTL_MS deduplication (2026-05-24)**: Per-role TTL existed as two independent `Record<string, ...>` maps — `ROLE_TTL` (jose TTL strings) in `lib/auth.ts` and `COOKIE_TTL_MS` (ms numbers) in `routes/auth.ts`. Both moved to `lib/auth-constants.ts`. Drift between the two caused potential silent broken-auth (JWT expired before cookie, or cookie expired before JWT). Any new role must be added to **both** maps in `auth-constants.ts`.

- **Cron patient recall deleted (2026-05-25)**: The daily 08:00 recall cron was a no-op — it ran a complex SQL query and logged the count, but the `db.insert(notificationsTable)` call was commented out. Deleted entirely. Do not re-add until SMS/WhatsApp (Phase 7) provides a delivery channel.

- **Phase 6 multi-tenancy reverted (2026-05-25)**: UUID PKs, `clinics` table, `clinic_id` FK on all PHI tables, and `clinicId` in JWT claims were partially implemented then rolled back at Mike's explicit request. Only cursor pagination and Redis doctor-scope cache were kept. Do not re-introduce `clinic_id` or UUID PKs until multi-tenancy is explicitly re-scoped. Integer serial PKs remain throughout.

- **Offset pagination → cursor pagination (2026-05-25)**: All 7 list endpoints (`patients`, `appointments`, `lab`, `xray`, `ultrasound`, `prescriptions`, `medical-records`) changed from `?limit&offset` to `?limit&cursor`. `cursor` is the integer `id` of the last record in the previous page. Response shape is now `{ data, nextCursor }` (patients: `{ patients, total, nextCursor }`). `ORDER BY id DESC` replaces `ORDER BY createdAt DESC` for stable pagination. `nextCursor: null` means last page. Frontend list pages have not been updated to use `useInfiniteQuery` — they still work (no cursor = first page) but load-more pagination is not wired.

- **VACUUM removed from app layer (2026-05-25)**: `cron.ts` had a nightly `VACUUM ANALYZE` run via `db.execute(sql\`VACUUM ANALYZE;\`)`. This is an autovacuum concern, not an application concern; it also cannot run inside a transaction. Configure PostgreSQL `autovacuum_vacuum_scale_factor` / `autovacuum_analyze_scale_factor` instead. Never call VACUUM from application code.

- **Cron now routes through validateTransition (2026-05-25)**: The no-show auto-transition used a direct `db.update` that bypassed the state machine entirely. Now calls `validateTransition("no_show", "scheduled", "system")` first — if the state machine rejects the path (e.g. someone removes `no_show` from the allowed transitions), the cron logs an error and aborts rather than silently drifting out of sync. "system" is a new bypass actor in `validateTransition`, alongside `super_admin`; it skips role checks but not source-state checks.

- **Audit before/after state columns (2026-05-25)**: Previously UPDATE audit entries stored `{ before: ..., after: ... }` in the unstructured `details` JSONB. Added dedicated `before_state` / `after_state` JSONB columns to `audit_logs`. `logAudit` now accepts them as the 6th and 7th arguments. Do not embed before/after diffs inside `details` — use the dedicated columns so compliance queries can target them with JSON path operators.

- **invoices.items JSONB dual-write (2026-05-25)**: Created `services_catalog` and `invoice_items` normalized tables. `createInvoice` now dual-writes to both `invoices.items` (JSONB, backward compat) and `invoice_items` (normalized). The JSONB column will be dropped via push-force once Phase 4 versioned migrations are in place. Do not add new code that reads from `invoices.items` JSONB — read from `invoice_items` instead.

- **Dead files removed (2026-05-24)**: `artifacts/api-server/src/fix-db.ts` (MFA cleanup script), `artifacts/clinic/src/lib/auth.tsx` (empty `export {}`), `scripts/post-merge.sh` (ran `drizzle push` unsafely on merge), `temp_dashboard_ref/` (abandoned Next.js app with npm lockfile). None of these should be re-created without deliberate purpose.

- **Versioned migrations (2026-05-25)**: `drizzle-kit push` replaced with `drizzle-kit generate` + `drizzle-kit migrate` for staging/prod. `drizzle.config.ts` no longer throws at module load when `DATABASE_URL` is unset (allows `generate` in CI without a DB). Initial migration `0000_rare_silver_fox.sql` captures the full 18-table schema. `db:push` / `db:push-force` remain for local dev iteration only — never run against staging or prod. Workflow: edit schema → `db:generate` → commit migration file → `db:migrate`.

- **ALLOWED_ORIGINS CORS env var (2026-05-25)**: `app.ts` CORS now reads `ALLOWED_ORIGINS` (comma-separated) in addition to `REPLIT_DOMAINS`. Each value is treated as a literal origin string (regex-escaped, exact match). Use this to allow the frontend when not deploying on Replit. Both env vars are additive; neither replaces the other.

- **PHI field-level encryption (2026-05-25)**: AES-256-GCM applied to `diagnosis`, `vitals` (medical_records), `medications` (prescriptions), `allergies`, `emergencyContact` (patients). Key = `FIELD_ENCRYPTION_KEY` env var (64 hex chars). Envelope format: `enc:v1:<iv_hex>:<tag_hex>:<data_base64>`. Module init throws in production if key absent; logs a warning in dev and runs unencrypted. Backward-compat: values not prefixed `enc:v1:` are returned as-is on decrypt — safe for existing dev data. JSONB columns (vitals, medications) are stored as encrypted string literals — Drizzle returns them as `string`; detect with `isEncrypted()` before calling `decryptJson()`. Never remove backward-compat path until all rows in prod have been re-encrypted with a migration script.

- **Treatment consent enforcement (2026-05-25)**: `hasActiveConsent(patientId, "treatment")` must return `true` before `createMedicalRecord` or `createPrescription` succeeds. Throws `ConsentRequiredError` (HTTP 422, error code 3010) otherwise. The check is at the service layer — routes need no change. When writing new services that create PHI, follow this pattern.

- **Right-to-erasure irreversibility (2026-05-25)**: `executeErasure` runs in a DB transaction and replaces PHI with `[ERASED]` / `1900-01-01` constants. There is no undo path. The audit log entry is written *outside* the transaction (immutable, survives rollback). Erasure requests must be `approved` before execution; only `super_admin` can execute. Per ADR-005: hard deletion of rows is prohibited — audit linkage must be retained. Future compliance queries should join on `erasure_requests.patientId` to detect anonymized subjects.

- **Break-glass SSE alert (2026-05-25)**: `activateBreakGlass` sends an SSE event to every `compliance_officer` via `emitToUser` for each officer's userId. If no compliance officers exist in the DB, the activation still succeeds (no error thrown). `alertSentAt` is set in the `break_glass_sessions` row only after all SSE calls complete. PHI must NOT flow through SSE payloads — the alert payload carries `sessionId`, `userId`, `patientId`, `justification`, and `activatedAt` only.

- **Docker build strategy (2026-05-25)**: Multi-stage `Dockerfile` for the api-server — deps stage installs pnpm workspace, build stage runs esbuild, runtime stage copies only `dist/*.mjs` + the `bcrypt` native addon (the only externalized non-Node runtime dep). `Dockerfile.clinic` builds the React SPA with Vite and copies static output into an `nginx:1.27-alpine` image. `nginx.conf` proxies `/api/*` to the `api` service with SSE buffering disabled, blocks `/metrics` at the edge, and adds a 1-year cache header for hashed assets. `docker-compose.yml` runs a one-shot `migrate` init container (reusing the `build` stage) to apply pending migrations before the API boots.
