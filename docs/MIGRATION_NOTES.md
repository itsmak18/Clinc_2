# Migration Notes — Lessons Learned / Deprecated Approaches

- **`translations` is now a named export from `hooks/i18n.tsx` (2026-06-02, F-03)**: The `const translations` object was made `export const translations` so the `i18n.test.ts` key-parity test can import it directly. If you have a barrel file or re-export layer that previously only exported `I18nProvider`, `useI18n`, and `I18nContextType`, add `translations` to it. The object's type (`typeof translations`) is unchanged — the `t()` function signature (`key: keyof typeof translations.en`) still holds. **Do not add new translation keys to only one language** — the `i18n.test.ts` parity guard (`EN keys ≡ AR keys`) will fail the `frontend-test` CI job immediately.

- **Migration 0020 creates `medicore_app` role — api/worker must switch DATABASE_URL (2026-06-02, F-01 fix)**: `0020_create_app_role.sql` creates the `medicore_app` role as NOSUPERUSER NOBYPASSRLS. The migrate container reads `./secrets/app_db_password` and calls `ALTER ROLE medicore_app LOGIN PASSWORD '...'` after migrations complete, then runs a smoke gate. api and worker now connect as `medicore_app` (not the bootstrap superuser). **Before deploying**: create `./secrets/app_db_password` (`openssl rand -base64 48 | tr -d '\n' > ./secrets/app_db_password`, `chmod 600`). The compose smoke gate will fail if this file is missing or the GRANT was not applied. **Rollback caveat**: rolling back past 0020 leaves the `medicore_app` role in Postgres but removes the GRANT. If you must roll back, manually run `DROP ROLE medicore_app` as the superuser AND switch the api/worker DATABASE_URL back to the bootstrap superuser before restarting — otherwise containers fail to connect. This migration is one-way; treat any rollback as a SEV-1 change. See RUNBOOK §0 and ADR-008-app-db-role.md.

- **Services now use `dbUnsafe` for non-tenant DB access (2026-06-02)**: The `@workspace/db` package exports `dbUnsafe` (alias of `db`). Services that legitimately bypass tenant context (pre-auth, tables without clinicId) must import `dbUnsafe` not `db`. The ESLint rule in `eslint.config.mjs` blocks bare `db` imports in `src/services/**` at lint time. If you add a new service that uses the raw DB client for non-tenant reasons: (1) import `dbUnsafe`, (2) add a one-line justification comment, (3) run `pnpm --filter @workspace/api-server run lint` to verify. If your use case is clinic-bearing, use `runInTenantContext(req.user!, async (tx) => …)` instead — never import `db` directly in a service.

- **Arabic clinical columns are in migration `0019_old_makkari.sql` — all nullable (2026-05-31, Phase 6)**: The migration adds `locale text NOT NULL DEFAULT 'en'` and `timezone text NOT NULL DEFAULT 'Europe/Istanbul'` to `clinics`, and `*_ar text` columns to `medical_records`, `prescriptions`, `lab_tests`, `xray_records`, `ultrasound_records`, and `services_catalog`. All Arabic columns are nullable — no NOT NULL constraint, no default. Apply before deploying the Phase 6 api binary: `pnpm --filter @workspace/db run db:migrate`. If you have existing rows the `ALTER TABLE ADD COLUMN` is safe with no backfill needed. **Never make the Arabic columns NOT NULL** — the bilingual design intentionally allows unilingual records. Enforcement belongs in UI labels only.

- **Doctor analytics does NOT cache — `logRead` is called on every hit (2026-05-31, Phase 6)**: `getDoctorAnalytics` and `listDoctorAnalytics` call `void logRead(req, "ANALYTICS", ...)` on every request. Do NOT wrap either function in `runtime.cache.getOrSet()` — caching skips the audit log (HIPAA gap) and would persist aggregated PHI in Redis. The analytics queries are already fast (no N+1 — all appointment + lab + xray data fetched in two round trips, revenue in one query per doctor). If performance becomes an issue, consider a separate read replica (see ROADMAP "Read replicas") not a cache.

- **`xray.service.ts` / `ultrasound.service.ts` update mutations accept `findingsAr` / `impressionAr` as top-level body fields (2026-05-31, Phase 6)**: These fields are not stored in their own columns — `findingsAr` and `impressionAr` for xray/ultrasound are passed through to the frontend via `reportAr` (encrypted). The frontend reads them back from the `reportAr` column (parsed from JSON if structured, or plain text). If the API spec is updated in a future pass to surface these as first-class fields, the service must parse `report_ar` accordingly. For now, the frontend stores them alongside English findings in `report` as a structured JSON `{ v: 1, findings, impression }` and separately passes `findingsAr` / `impressionAr` to the update mutation as `any`-typed extras — this works because the service accepts the full body and maps whichever columns are present.

- **`docker-compose.prod.yml` gains four containers + two secrets + five volumes (2026-05-31, Phase 4 Operational Hardening)**: New services `prometheus`, `alertmanager`, `grafana`, `backup`. New secrets `grafana_password` and `backup_ssh_key` — both must exist (mode 0600) at `./secrets/` before `up`. New volumes `prometheus_data`, `alertmanager_data`, `grafana_data`, `backup_data`, `backup_metrics` — mount host paths or NFS for `backup_data` to survive container lifetime. New required `.env` vars (compose rejects missing `:?` placeholders): `SMTP_SMARTHOST`, `SMTP_FROM`, `SMTP_AUTH_USER`, `SMTP_AUTH_PASS`, `ALERT_EMAIL_TO`, `BACKUP_GPG_RECIPIENT`, `BACKUP_RSYNC_TARGET`. If you are pulling this branch into an existing prod deployment, **add these env vars and secret files before `docker compose up -d`** or compose parsing will fail before any service starts.

- **API/worker now use `image:` with `build:` fallback (2026-05-31, Phase 4)**: The `api` and `worker` services resolve their image from `${API_IMAGE:-medicore-api:latest}` (worker also falls back to `WORKER_IMAGE`). Pre-Phase-4 deployments rebuilt from source on every `up -d`; the new pattern lets you `up -d --no-build` after a CI build pushes a tagged image. If your existing CI does not push images, set `API_IMAGE=medicore-api:latest` in `.env` and keep using `up -d --build`. **There is no `down` migration**: rolling back a deploy reverts code only; if the bad release shipped a destructive Drizzle migration (dropped column, narrowed type, RLS policy that breaks reads), the choices are roll-forward-hotfix or restore-from-backup. See [RUNBOOK.md §10.2](../RUNBOOK.md).

- **Grafana is intentionally not exposed via Caddy (2026-05-31, Phase 4)**: The `grafana` container binds `127.0.0.1:3000` on the host and attaches to `backend` only — no `frontend` network, no `handle_path /grafana/*` in `caddy/Caddyfile`. This was an explicit operator decision: the app surface stays minimal on the internet, admin tooling reached via `ssh -L 3000:localhost:3000 deploy@host`. If you later expose Grafana publicly, add TLS + auth in front and revisit the `GF_SERVER_ROOT_URL` env — the current config assumes localhost access.

- **Alertmanager email config uses env-var interpolation, not file secrets (2026-05-31, Phase 4)**: SMTP credentials live in the alertmanager container's `environment:` block, not in `./secrets/`. This is a deliberate trade-off — Alertmanager's YAML supports `${VAR}` interpolation but not file-based secrets without a sidecar template renderer. The result: `docker inspect alertmanager` exposes `SMTP_AUTH_PASS`. If your SMTP provider supports app-specific tokens (Gmail app password, SES SMTP creds), use one. Do NOT reuse the same SMTP password elsewhere.

- **Backup container shells out to `apk add` at startup (2026-05-31, Phase 4)**: `gnupg`, `openssh-client`, `rsync` are not in the base Dockerfile build target — the backup entrypoint installs them on first run (and on every restart). This is intentional: the api/worker runtime images stay minimal (no GPG/SSH/rsync in the attack surface of the request-handling containers). If you ever change the backup container to share the runtime image, you must also add these packages to the Dockerfile or backup will fail with "command not found". Network egress for `apk` requires the `backend` network keep `internal: false` (current default).

- **`runtime.scopeCache` is now part of `/api/health` readiness (2026-05-31, Phase 4)**: `checkReadiness()` performs `SET health:ping 1 EX 5` + `GET` against `runtime.scopeCache`. In memory mode (`SESSION_STORE=memory`, dev default) `scopeCache` is undefined and the check reports `{ status: "ok", store: "memory" }` without I/O — no test breakage. In production (`SESSION_STORE=redis`) a Redis outage flips `ok=false` → 503 → Docker healthcheck → container restart. **If you add a new Redis-backed store to `Runtime`, prefer extending the existing health check over adding a separate one** — collapse them into a single Redis roundtrip so we don't multiply latency on the health path.



- **`medical_records.is_global` / `global_reason` columns dropped — apply migration `0011_clinic_notices.sql` (2026-05-29)**: `ALTER TABLE medical_records DROP COLUMN is_global / global_reason` runs inside this migration after creating `clinic_notices` and migrating any `is_global=true` rows. If your codebase has any reference to `medicalRecordsTable.isGlobal`, `medicalRecordsTable.globalReason`, or `PATCH /medical-records/:id/global-flag`, remove it — these no longer exist. `assertMedicalRecordInScope` in `scope.ts` now only checks `doctorId` ownership; the isGlobal bypass is gone. If you have tests that mock `medicalRecordsTable` with an `isGlobal` field, remove it from the mock shape. The deny reason logged by `assertMedicalRecordInScope` changed from `"record_not_owned_or_global"` to `"record_not_owned"` — update any test assertions that check for the old string.

- **`style-src 'unsafe-inline'` is no longer in the production CSP (2026-05-29)**: React's `style={}` prop uses `element.style.*` DOM API — browsers apply `style-src` only to static HTML `style` attributes and `<style>` elements, not to JavaScript-set styles from trusted scripts. If any future dependency injects a `<style>` block at runtime (e.g. a CSS-in-JS library), you must add `'unsafe-inline'` back to `styleSrc` in `lib/csp.ts` AND `STRICT_CSP` in `vite.config.ts`, and remove or update the `csp.test.ts` regression guard. `chart.tsx`'s `ChartStyle` was the only `<style>` injector in this codebase; it was replaced with CSS custom properties set via inline `style={}` on the container. **Dark-mode `theme.dark` values in `ChartConfig`** are not supported without `unsafe-inline` — define dark-mode chart colors as CSS variables in `index.css` instead.

- **`audit_integrity_checks` requires migration `0010_audit_integrity_chain.sql` before the nightly cron fires (2026-05-29)**: `recordDailyIntegrity()` inserts into `audit_integrity_checks`. If the table doesn't exist, the nightly 02:00 cron throws and the error is logged but does not crash the process. Apply the migration before deploying: `pnpm --filter @workspace/db run db:migrate`. The table has a UNIQUE constraint on `checked_date` — running the cron twice for the same day (e.g. after a bug fix) upserts the row rather than duplicating it.

- **`verifyIntegrity()` uses the stored `prevHash`, not a freshly derived one (2026-05-29)**: When re-verifying a day's hash, `verifyIntegrity()` fetches the `prevHash` from the stored record and uses that to re-derive the expected `rootHash` — it does NOT re-query the previous day's record. This is intentional: the goal is to detect row-level tampering in the target day's `audit_logs`, not chain drift. If you want to verify the entire chain from genesis, call `verifyIntegrity()` iteratively from the earliest date forward. A mismatch at day N does NOT automatically imply day N−1 is clean.

- **`@opentelemetry/resources` v1.30+ dropped the `Resource` class — use `resourceFromAttributes` instead (2026-05-29)**: The named export `Resource` was removed from `@opentelemetry/resources` in the v2 API migration. Import and call `resourceFromAttributes({ [ATTR_SERVICE_NAME]: "…", … })` instead of `new Resource({ … })`. TypeScript will surface this as "only refers to a type, but is being used as a value" at compile time. The function signature is identical except it's called as a function, not a constructor.

- **`lib/db` declarations must be rebuilt after adding new schema files (2026-05-29)**: `lib/db/tsconfig.json` has `"composite": true` and `"emitDeclarationOnly": true`. The api-server's TypeScript project reference consumes the generated `lib/db/dist/*.d.ts` declarations, not the source. After adding new schema files (e.g. `doctor_patients.ts`), run `pnpm exec tsc -p lib/db/tsconfig.json` from the workspace root to regenerate declarations before typechecking the api-server. If you skip this step, typecheck reports "has no exported member" for any symbol from the new file even though tests pass (tests mock `@workspace/db` entirely).

- **`@opentelemetry/*` packages are bundled (not externalized) in the production build (2026-05-29)**: `build.mjs` previously listed `"@opentelemetry/*"` in the `external` array. This was removed so OTel packages bundle into `dist/index.mjs`. The minimal production Docker runtime image only copies `node_modules/bcrypt` — any externalized package not present at runtime causes a module-not-found crash. OTel packages are pure JS and bundle cleanly. If you add `@opentelemetry/auto-instrumentations-node` in future (for Express/pg auto-instrumentation), note that it monkey-patches `require()` calls and may not work correctly from a bundled ESM file — keep it external and update the Dockerfile runtime stage to copy it.

- **`getDoctorPatientScope` no longer queries `appointmentsTable` — update test mocks accordingly (2026-05-29)**: `scope.ts` previously used `db.selectDistinct` on `appointmentsTable` for doctor patient-scope lookups. It now uses `db.select` on `doctorPatientsTable`. Any test that mocks `@workspace/db` and exercises `getDoctorPatientScope` (directly or via `assertPatientInScope`) must: (1) replace `appointmentsTable: { patientId, doctorId }` with `doctorPatientsTable: { patientId, doctorId }`, (2) change the chain mock from `db.selectDistinct` to `db.select`, (3) add `insert: vi.fn()` for `recordDoctorPatientLink` coverage. The `selectDistinct` property is no longer used anywhere in `scope.ts` — if your mock still declares it, `db.selectDistinct` will be a dead stub. **Migration `0009_smooth_hellfire_club.sql`** must be applied before deploying the updated `scope.ts` and `appointments.service.ts` — the table is used on every authenticated doctor request.

- **Infrastructure Prometheus alerts are safe to commit without their exporters (2026-05-29)**: `prometheus-alerts.yml` now includes rules for `redis_memory_used_bytes`, `node_filesystem_avail_bytes`, and `probe_ssl_earliest_cert_expiry` — metrics that require `redis_exporter`, `node_exporter`, and `blackbox_exporter` respectively. If these exporters have not been deployed, the alert rules produce empty vector results in Prometheus (no matching series). An empty vector never satisfies a threshold comparison, so the alerts stay inactive and generate no false pages. This is the standard practice: commit alert rules ahead of exporter deployment so Alertmanager routing and notification channels can be pre-wired. **`for: 0m` on `AuditLogPermanentLoss`** is intentional — this is a HIPAA incident-class event and zero grace period is correct. Any non-zero `for:` duration would hide the first occurrence.

- **`pool` must be in the `@workspace/db` mock for any test that imports `app` (2026-05-29)**: `lib/metrics.ts` imports `pool` from `@workspace/db` and accesses `pool.totalCount`, `pool.idleCount`, `pool.waitingCount` in `getMetrics()`. Any test file that imports `app` (which registers `/metrics` via `getMetrics`) and does not provide `pool: { totalCount: 0, idleCount: 0, waitingCount: 0 }` in the `@workspace/db` mock will get `TypeError: Cannot read properties of undefined (reading 'totalCount')` on the first `/metrics` request. The full thenable-proxy mock pattern used in `metrics.test.ts` and `phase2.flagON.integration.test.ts` already includes `pool`.

- **`isStrictPasswordPolicyEnabled()` is gated by the master Phase 2 flag (2026-05-28)**: In `lib/auth-constants.ts`, `isStrictPasswordPolicyEnabled()` returns `isPhase2Enabled() && process.env.PHASE2_STRICT_PASSWORD_POLICY === "true"`. Setting only `PHASE2_STRICT_PASSWORD_POLICY=true` without also setting `PHASE2_DEVICE_TRUST_ENABLED=true` has no effect — the function always returns `false`. All other sub-flags (`isEmailVerifyEnabled`, `isStepUpEnabled`, `isCspReportEnabled`) share the same gate. **In tests**: when asserting WEAK_PASSWORD behavior on `/auth/reset-password`, set BOTH env vars. Also note that Zod's `resetSchema` enforces `newPassword: z.string().min(8)` independently of the strict policy — passwords shorter than 8 chars get `VALIDATION_ERROR`, not `WEAK_PASSWORD`.

- **Phase 2 anonymous routes must register before domain routers (2026-05-28)**: Every domain router (users, patients, appointments, etc.) mounts a global `router.use(requireAuth)` with no path prefix. Express applies it to ALL requests the router sees — not just those matching routes within it. Unauthenticated POST/DELETE requests reach `evaluate()`, which checks CSRF before token presence for `write`/`privileged` scopes on mutation methods. The result: missing-auth tests get 403 AUTH_CSRF_MISSING instead of 401 AUTH_NO_TOKEN. **Fix**: register any new unauthenticated route's router in `routes/index.ts` BEFORE `usersRouter` (and before all other domain routers). Currently: `jwksRouter → healthRouter → authRouter → devicesRouter → passwordResetRouter → cspReportRouter → usersRouter → ...`. Any new public endpoint must follow the same position rule. **For test authors**: integration tests that expect a 401 on mutation endpoints must provide a matching `_csrf` cookie + `X-CSRF-Token` header to bypass the CSRF gate first; otherwise `evaluate()` returns 403 before checking the token.

- **`UserPasswordResetBody` / `ResetPasswordBody` naming (2026-05-28)**: OpenAPI spec originally declared `ResetPasswordBody` for the admin reset path (`POST /auth/admin-reset/{userId}`) but this name collided with the Phase 2 self-service schema `ResetPasswordBody` used by `POST /auth/reset-password`. The admin-reset schema was renamed to `UserPasswordResetBody` during the Phase 2 OpenAPI sync. If you have Orval-generated code that references `ResetPasswordBody` in the context of admin password resets, it must be updated to `UserPasswordResetBody`. The self-service `POST /auth/reset-password` body schema retains the name `ResetPasswordBody`.

- **`clinicId` is now required on `AuthUser` / `AuthRequest.user` (2026-05-28)**: `AuthUser.clinicId: number` and `AuthRequest.user.clinicId: number` are required fields. The policy kernel fills the value with `payload.clinicId ?? 1` for backward compat with existing JWTs. **Every PHI service query MUST include `eq(table.clinicId, req.user!.clinicId)` in its conditions array.** Missing this filter means any authenticated user of another clinic can read any PHI row from the same table. Test mocks that supply `req.user` via `as unknown as AuthRequest` or `as any` do not need updating (casts bypass the type check), but any mock that constructs the user object literally must now include `clinicId`. **`usersTable` gains `clinic_id integer NOT NULL DEFAULT 1`** — apply migration `0008_acoustic_cassandra_nova.sql` before deploying. Existing rows in `users`, `operations`, `inventory` populate with value `1`. `TokenPayload.clinicId` is optional (old tokens without the claim still verify; kernel fills `?? 1`). Once per-role TTLs rotate (max 4h), every active JWT carries the claim.

- **SSE `event: shutdown` is replaced by `event: reconnect` with jitter (2026-05-28)**: `closeAllSSEClients()` no longer sends `event: shutdown\ndata: {"reason":"server_shutdown"}`. It now sends `retry: <jitterMs>\nevent: reconnect\ndata: {"reason":"server_draining","retryAfter":<jitterMs>}\n\n` where jitter is randomized per connection (5 000–15 000 ms). Frontend `use-notifications-stream.ts` handles the `reconnect` event with a `setTimeout(connect, retryAfter)` delay. Any external SSE client or test that asserts `event: shutdown` must be updated. The `SHUTDOWN_TIMEOUT_MS` default has been raised from 25 000 to 30 000 ms; ensure the host process manager gives at least 35s before SIGKILL (`stop_grace_period: 35s` is now in both compose files). `SSE_DRAIN_MS` env var (default 10 000 ms) controls how long existing connections are held open before the reconnect event is sent — set to 0 in test environments.

- **Erasure restores require re-anonymization within the blackout window (2026-05-28)**: `executeErasure()` now sets `erasure_blackout_until = executedAt + BACKUP_RETENTION_DAYS` on the `erasure_requests` row. Any backup produced before that timestamp still contains pre-erasure PHI. If you restore from such a backup, you MUST re-apply the anonymization SQL for each affected patient before promoting the restore — see RUNBOOK §2.2 step 5. `backup-verify.mjs --restore` enforces this automatically (fails the drill if active blackouts are detected). Apply migration `0007_wide_zarda.sql` with `pnpm --filter @workspace/db run db:migrate` — instant metadata-only `ALTER TABLE` change.

- **Audit write is now outbox-based — fire-and-forget pattern retired (2026-05-28)**: `logAudit()` no longer writes directly to `audit_logs`. It now writes to `audit_outbox` (an unindexed, FK-free queue table). A background drain worker (`drainAuditOutbox()`, called every 5 s from `startAuditDrain()` in `cron.ts`) transfers rows to `audit_logs` with exponential backoff (5 s → 30 s → 2 min → 10 min) and up to 5 attempts. Rows exhausted after 5 attempts are counted in `audit_log_write_failures_total` and logged at `audit_outbox_row_exhausted`. **Test mocks that stub `@workspace/db`** must now include `auditOutboxTable: {}` — previously `auditLogsTable` was the only table `logAudit()` touched. Any new test file that mounts the Express app (and therefore triggers `logAudit()` calls) must add `auditOutboxTable` to its DB mock. The Prometheus metric `audit_log_write_failures_total` now means **permanent loss** (exhausted rows), not temporary failures. Prometheus alert for `audit_outbox_drain_failed` is more important than the counter. **Apply migration `0006_odd_machine_man.sql`** before deploying: `pnpm --filter @workspace/db run db:migrate`.

- **`invoices.items` JSONB column dropped — `invoice_items` is now the sole source of truth (2026-05-28)**: The dual-write pattern (write to both JSONB column and normalized `invoice_items` table) has been eliminated. The column is removed from `invoicesTable` in `billing.ts` and from the DB via migration `0005_charming_psynapse.sql`. Apply before deploying the new api binary: `pnpm --filter @workspace/db run db:migrate`. The API response shape is unchanged (`items: InvoiceItem[]` is still returned from all billing endpoints — now sourced via a normalized join instead of the JSONB read). **Never add `items: jsonb(...)` back to `invoicesTable`** — any future line-item feature belongs in `invoice_items`. The `itemsSchema` Zod validator in `lib/jsonb-schemas.ts` is retained for input validation in `createInvoice()` — do not remove it even though the JSONB column is gone.

- **JWT is now EdDSA asymmetric — HS256 is gone (2026-05-28)**: `lib/jwt-secret.ts` was completely rewritten. JWT signing now uses an Ed25519 key pair (`JWT_PRIVATE_KEY` PKCS8 PEM + `JWT_PUBLIC_KEY` SPKI PEM) via `jose`. The algorithm header changed from `{ alg: "HS256" }` to `{ alg: "EdDSA", kid: "<kid>" }`. All existing HS256 sessions are invalidated on deploy — users will get a 401 and must re-login. This is a one-time migration cost. **`SESSION_SECRET` is no longer the JWT signing key** — it is now the HMAC key for device fingerprinting (`lib/device-fingerprint.ts`) only. Do not use `SESSION_SECRET` for JWT operations. The `JWT_SECRET: Uint8Array` export from `lib/jwt-secret.ts` is preserved for `device-fingerprint.ts` backward compat — do not remove it. The public key set is advertised at `GET /api/.well-known/jwks.json` (Cache-Control: public, max-age=3600). Key rotation overlap: set `JWT_PREV_PUBLIC_KEY` + `JWT_PREV_KID` in the entrypoint to advertise both old and new public keys during rotation — old tokens verify until they expire naturally. See `SECURITY.md §"JWT key rotation"` for the 6-step quarterly rotation procedure. **Deploy action required**: create `./secrets/jwt_private_key` + `./secrets/jwt_public_key` (mode 0600) before next prod restart. Atomic generator: see `secrets/README.md`.

- **Field-encryption envelope is now KID-aware (2026-05-27)**: `lib/field-encryption.ts` now writes `enc:v2:<kid>:<iv>:<tag>:<data>`. Legacy `enc:v1:<iv>:<tag>:<data>` envelopes are still decrypted (via `kid="1"` key) but new writes always produce `enc:v2:`. `FIELD_ENCRYPTION_KEY` feeds `kid="1"`. Optional `FIELD_ENCRYPTION_KEY_NEXT` feeds `kid="2"` during rotation. `FIELD_ENCRYPTION_KEY_WRITE_KID` (default `"1"`) controls which kid new writes use. **Never delete `FIELD_ENCRYPTION_KEY` while `enc:v1:` or `enc:v2:1:` envelopes exist in the DB** — the module throws on decrypt, data is effectively unreadable. See `SECURITY.md` for the six-step rotation procedure.

- **PHI-decryption-capable secrets are now file-mounted in production (2026-05-27)**: `SESSION_SECRET`, `FIELD_ENCRYPTION_KEY`, and `METRICS_TOKEN` were moved from the `environment:` block of `docker-compose.prod.yml` to Docker secrets (`/run/secrets/*`). **Before the next `docker compose -f docker-compose.prod.yml up -d`** you must create all three files at `./secrets/{session_secret,field_encryption_key,metrics_token}` with `chmod 600`. The entrypoint uses `test -s` to fail-close if any file is missing or empty — the container will not start. `JWT_SECRET` env var is fully removed (dead code — `lib/jwt-secret.ts` reads `SESSION_SECRET` exclusively). `REDIS_PASSWORD` is still env-passed (interpolated into `REDIS_URL` at compose parse time).

- **Express trust proxy is now set (2026-05-27)**: `app.set("trust proxy", "loopback, linklocal, uniquelocal")` was added to `app.ts` before all middleware. Behind Caddy on the docker bridge network `req.ip` previously resolved to the Caddy container IP, causing every rate-limit key and audit IP field to collapse to one identity. This is now correct. The regression test in `trust-proxy.test.ts` pins the setting — do not remove it or change the trust string without also updating those tests and verifying the rate-limiter works correctly with multi-IP XFF headers.

- **Cursor pagination is now complete end-to-end (2026-05-27)**: Backend list endpoints moved to cursor in Phase 6. Frontend call sites were still passing `offset: 0`. All 12 call sites (11 pages + `components/CommandPalette.tsx`) have been migrated. OpenAPI spec updated: `offset` → `cursor` on `/patients` and `/appointments`; new `PaginatedAppointments` schema. A CI grep guard in `ci.yml` now blocks `offset:N` params in `artifacts/clinic/src/pages/` and `components/` (except `AuditLog.tsx`). **Do not pass `offset:` to any generated hook** — use the cursor-based params or leave the param unset (returns first page). `AuditLog.tsx` is the only intentional offset survivor and is explicitly excluded from the CI guard.

- **`Appointments.tsx` and `DoctorDashboard.tsx` runtime bug fixed (2026-05-27)**: The OpenAPI spec previously declared `GET /appointments` response as `array of Appointment`. Backend actually returns `{ data: Appointment[], nextCursor: integer | null }`. TypeScript believed the spec; calling `.map()` on the response object would throw `TypeError` at runtime. The pagination spec migration corrected this — both pages now destructure `.data` from the response. Symptom in the wild: "Appointments list always empty" or "Recent patients panel never populates".

- **`pharmacist` can now read prescriptions (2026-05-27)**: `routes/prescriptions.ts` `GET /prescriptions` and `GET /prescriptions/:prescriptionId` were missing `pharmacist` from their `requireRole(...)` arrays. Pharmacists were being redirected to `/prescriptions` on login (their landing page) and immediately receiving 403. Fixed. The route-access contract test (`route-access.contract.test.ts`) now pins this invariant on every PR.
